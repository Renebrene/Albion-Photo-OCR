## 🧩 Основные изменения

### 1. **Физическая структура**
```text
INPUT
│
├── originals/              ← Оригинальные фото (не сортируем)
│   ├── IMG_001.JPG
│   └── Вавилова52_12.JPG
│
└── output/                 ← Все производные данные
    ├── photobase.db       ← Основная БД (виртуальная сортировка)
    ├── previews/          ← Превью (кэш)
    ├── fingerprints/       ← Хеши
    ├── qwen_results/      ← JSON-ответы Qwen
    └── runs/              ← История запусков
```

### 2. **Виртуальная сортировка в БД**
- **Фото не перемещается в папки**, а **хранится в `originals/`**.
- **БД содержит метаданные**:
  ```text
  photo_id
  original_path
  file_hash
  fingerprint
  recognized_address
  qwen_json
  preview_path
  status
  ```

## 🔄 Реактивный UI: Грид как живой интерфейс

### ✅ Немедленное обновление
- **Грид не ждет завершения обработки**. Он:
  1. Запрашивает БД: "Какие фото уже известны?"
  2. Показывает превью
  3. Для каждой фотографии:
     - Если DINO обработал → показывает адрес
     - Если Qwen завершил → показывает описание
     - Если Qwen работает → "Анализируется..."

### 🧾 Пример:
```text
11:01:00  DINO обработал 1 фото
11:01:01  → запись в БД
11:01:01  → preview создан
11:01:01  → грид показывает фото

11:01:02  Qwen начал анализ
11:01:09  → Qwen закончил
11:01:09  → грид показывает описание
```

## 🧹 Синхронизация оригинала ↔ превью

### 📌 Правила:
- **Оригинал всегда главный**.
- **Превью — кэш**, который:
  - Создается при первом открытии
  - Удаляется, если оригинал исчез
  - Пересоздается, если превью удалено

### 📌 Пример:
```text
input/Вавилова52_12.JPG
hash: a83f91...
preview: output/previews/a8/a83f91....webp
```

## 🧹 Удаление: Синхронизация с оригиналом

### 📌 Логика:
- **Удалить → удаляем оригинал**
- **После удаления:**
  - Удаляем запись из БД
  - Удаляем превью

### 📌 Пример:
```text
12:00:00  Пользователь нажал "Удалить"
12:00:01  Удаляем input/Вавилова52_12.JPG
12:00:02  Удаляем запись из БД
12:00:03  Удаляем preview
12:00:04  Грид убирает фото
```

## 🧠 Параллельные процессы: DINO + Qwen

### 📌 Архитектура:
```text
INPUT
│
├── originals/
│
└── output/
    ├── photobase.db
    └── qwen_results/
```

### 📌 Потоки:
- **DINO (CPU)**: Распознавание адресов, хеширование
- **Qwen (GPU)**: Генерация описаний, метаданные
- **БД**: Хранит все состояния (status, progress, errors)

### 📌 Пример:
```text
12:00:00  Фото появилось
12:00:01  DB зарегистрировала фото
12:00:02  Превью создано
12:00:03  Грид показывает фото

12:00:05  DINO → 95_v33
12:00:06  Грид показывает "95_v33"

12:00:08  Qwen начал анализ
12:00:15  Qwen закончил
12:00:15  Грид показывает Ozon fresh
```

## 🧠 Очереди для Qwen

### 📌 Логика:
- **Qwen работает из очереди `qwen_queue`**:
  ```text
  photo_id | status | priority | created_at
  ```
- **Если Qwen остановлен**:
  - Задачи сохраняются в очереди
  - При запуске продолжаются

### 📌 Пример:
```text
100 фото обнаружено
100 DINO обработано
100 попало в Qwen queue
37 Qwen обработал
63 waiting

Запускаем Qwen снова:
63 waiting → продолжает работу
```

### 📌 Пример:

## 🧠 Итог: Преимущества новой архитектуры

| 📌 Старая система | ✅ Новая архитектура |
|-------------------|---------------------|
| Физическая сортировка | Виртуальная сортировка |
| Грид зависит от папок | Грид зависит от БД |
| Нужно ждать обработки | Показывает результат сразу |
| Qwen запускается отдельно | Qwen работает очередью |
| Сортировка → потом Qwen | DINO + Qwen параллельно |
| Preview связан с копией | Preview связан с `photo_id` |
| Удаление сложнее | Оригинал + preview синхронно |
| Download может отдавать копию | Download всегда оригинал |
| Перезапуск может быть неудобным | Queue продолжает незавершённые задачи |
