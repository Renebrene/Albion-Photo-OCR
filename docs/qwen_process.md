# QWEN — параллельный процесс метаданных (заметки)

**Статус:** заметки по историческим материалам `111/` (легаси-проект `scene_fingerprint_mvp_v02`).
**Реализовано (2026-10-13) в минимальном виде:** `app/qwen/` + `schema/007_qwen.sql` (`photo_qwen`) + `job_type = QWEN_PHOTO`
в очереди. Default модели из env — `qwen3-vl:8b` (`app/qwen/config.py`), но рабочая модель выбирается в рантайме через настройки
(в текущем стенде выбрана `qwen3-vl:4b-instruct`). Поля `description/address/client/brand/category/tags`.
Детали реализации — в [`frontend_quasar.md`](frontend_quasar.md) §6, «Срез 5». Ниже — исторический контекст.

**Коротко:** QWEN — отдельный процесс, который независимо от DINO обогащает фотографии текстовыми метаданными (описание, адрес, клиент, бренд, категория и структурные JSON-поля) через локальную VLM-модель в Ollama. Работает параллельно DINO по одним и тем же `photo_id`.

## 1. Место в архитектуре

Источник: `111/chat_chunks/chunk_131.md` (~520–700), `chunk_234.md`.

```text
                    PostgreSQL
                         │
              ┌──────────┴──────────┐
              │                     │
        dino_status=pending   qwen_status=pending
              │                     │
              ▼                     ▼
       DINO WORKER             QWEN WORKER
       1 процесс               1 процесс
       CPU                     GPU
              │                     │
              └──────────┬──────────┘
                         ▼
                       photos
```

Ключевой принцип: **DINO и Qwen независимы**. Для одного фото:

```text
PH_00000527
      ├──► DINO ──► dino_status=ok
      └──► QWEN ──► qwen_status=ok
```

а не последовательная цепочка `DINO → Qwen → следующая`.

Планировалось в супервизоре (`app/pipeline/supervisor.py`, `run_pipeline()`):

```text
                    ┌── Hybrid v12 ──► внутренний DINO 33
                    │                 └─► TOP1-5 + соседи + hybrid_final_id → PostgreSQL
daily ─> photo_id ──┤
                    └── Qwen ────────► описание → PostgreSQL
```

Позже планировалось убрать отдельный `DINO_WORKER` из супервизора и запускать DINO внутри Hybrid v12, оставив Qwen как параллельную ветку.

## 2. Как работает воркер

- Один постоянно живущий процесс; модель загружается один раз (для DINO — `SceneEmbedder`; для Qwen — Ollama сама держит модель).
- Забор задачи: `SELECT ... FOR UPDATE SKIP LOCKED` по статусу `pending`.
- Обработка одного фото → запись статуса и полей.
- Файлы (легаси): `app/workers/qwen_worker.py`, `app/pipeline/supervisor.py`.

## 3. Модель и транспорт

- Ollama: `http://localhost:11434/api/generate`, `http://localhost:11434/api/chat`.
- Основная модель: `qwen3-vl:4b-instruct`.
- В экспериментах упоминались также `qwen2.5-vl:3b` и `llama3.2-vision:11b`.
- Скрипты генерации/тестов: `scripts/qwen4b_output_v01.py`, `qwen4b_output_v01_before_compact_prompt.py`, `scripts/banner_qwen4b_test_v01.py`, `banner_qwen25vl_test_v01.py`, `banner_model_compare_v0x.py`.
- Роль Qwen: **визуальный помощник / описание / проверка**, не основной цикл распознавания. Ориентир по скорости — порядка нескольких секунд на фото (в обсуждениях фигурировало ~8.75 с/фото).

## 4. Поля вывода (легаси-таблица `photos`)

Из `app/web/photo_db.py`, `app/web/components/search.py`:

- скалярные: `address`, `client`, `brand`, `category`, `description`, `confidence`;
- статус/время: `qwen_status`, `qwen_time_sec`;
- структурные JSON: `text_json`, `colors_json`, `objects_json`, `environment_json`, `image_quality_json`, `camera_view_json`, `scene_objects_json`, `analysis_quality_json`, `raw_json`;
- служебное: `imported_at`.

Отмеченные особенности:
- клиенты «появляются динамически от Qwen» → отдельная сущность/таблица;
- идея «реестра нормализации сущностей» — не править исходные данные Qwen, а нормализовать отдельно (`chunk_087.md` ~2197);
- поиск по Qwen-данным в легаси был только по PostgreSQL (без DINO) — `search_database()`.

## 6. Реализовано в текущем репозитории (2026-10-13)

- Отдельная таблица `photo_qwen` (`schema/007_qwen.sql`), независима от DINO/INGEST; job `QWEN_PHOTO` в `job_queue`.
- Поля: `description, address, client, brand, category, tags[]`. Легаси-JSON-поля (colors/objects/environment/quality) **не переносились** — в промпте их нет.
- **Стабильность парсинга (2026-10-13)**: ответ иногда обрывался по лимиту токенов (`done_reason: "length"`) → JSON не закрывался → `"no JSON object"`. Добавлены `options.num_predict = 512` и ограничение «tags не более 10»; ранее упавшие 2 фото + 1 без строки (MPO) обработаны. Итог: **256/256 DONE**.
- Диагностика/повтор: `GET /v1/qwen/stats` (counts + `failed_photo_ids`); `POST /v1/jobs/qwen {"only_failed": true}` — повторный прогон упавших; кнопка в UI «Настройки → Метаданные QWEN».
- NL-поиск: job `NL_SEARCH` (см. `docs/frontend_quasar.md`, Срез 17).

### 6.1 Провайдеры и keep-alive (2026-10-13)

- **Провайдер** выбирается на рантайме (таблица `app_settings`, поля в UI): `ollama` (локально, по умолчанию) или `openai` — OpenAI-совместимый облачный endpoint (`base_url` + `model` + `api_key`). Ключ хранится в настройках и **маскируется** в ответах (`public_settings`), наружу не отдаётся. Облако — осознанный opt-in: изображения уходят на внешний сервис (в UI есть предупреждение).
- API: `GET /v1/qwen/settings` (маскированный вид), `PUT /v1/qwen/settings` (provider/model/base_url/api_key/keep_alive/unload_on_idle), `GET /v1/qwen/models` (модели активного провайдера), `POST /v1/qwen/unload` (для облака — no-op).
- **Keep-alive**: `QWEN_KEEP_ALIVE` (по умолчанию `10m`) держит локальную модель резидентной между заданиями; `QWEN_UNLOAD_ON_IDLE` заставляет воркер выгружать её, когда очередь опустела. Ручная выгрузка остаётся.
- **Замер (2026-10-13, qwen3-vl:4b-instruct, RTX 3060)**: одно фото cold **9,35 с** vs warm **2,60 с** — ускорение **3,59×**; `ollama ps` подтверждает резидентность. Ожидаемый эффект на очередь ≈ вдвое меньше суммарного времени относительно прежнего `keep_alive: 0` (сохранённое среднее 5,3 с/фото).

### 6.2 Что именно уходит в модель (2026-10-14)

- **Вход — MIDDLE-превью, а не оригинал.** `processor.analysis_input(photo_id, source_path)` подставляет `data/preview/middle/<photo_id>.jpg`, если файл есть, и только при его отсутствии отдаёт оригинал. Превью — это уже тот же JPEG ≤1280 px, который `encode_image()` собрал бы из оригинала, поэтому модель видит то же самое, но оригинал (возможно, лежащий на сетевом томе) повторно не читается и не декодируется.
- **Масштаб**: длинная сторона ограничена `MAX_IMAGE_SIDE = 1280`; EXIF при перекодировании в JPEG теряется (наружу не уходит).
- **Бюджет ответа**: `max_output_tokens` (по умолчанию 512 для пакетного прогона; для поискового запроса поднимается до 1024), `temperature: 0`, `format: json`, `think: false`.
- **Обрыв на рассуждениях**: если модель игнорирует `think: false` и её «мысли» съедают бюджет, JSON не приходит — `parse_result` кидает `QwenParseError` с сырым текстом (см. Срез 29 в `frontend_quasar.md`).

### 6.3 Статистика карточки QWEN (2026-10-16)

`GET /v1/qwen/stats` отдаёт снимок для карточки «Настройки → Метаданные QWEN»:

- `photos` — размер базы (`count(*) FROM photos`). Прежнее «ВСЕГО» суммировало
  строки `photo_qwen`, а фото, которое ни разу не ставили в очередь, строки не
  имеет вовсе, поэтому сумма занижала базу.
- `counts` — статусы `photo_qwen` (PENDING/RUNNING/DONE/FAILED), `processed`
  (= DONE) и `remaining` (= `photos − processed`).
- `failed_photo_ids` — как раньше, для кнопки «Повторить для упавших».
- `runs` — по каждому источнику запуска: сколько заданий, сколько упало и когда
  последний раз завершался (`max(finished_at)`).

Источник запуска пишется в `payload.source` задания `QWEN_PHOTO`:
`manual` (кнопка в «Настройках»), `automation` (планировщик), `pipeline`
(внеочередной прогон «Обновление базы»). Задания, созданные до появления поля,
читаются как `manual`. Окно показывает «обновляется автоматически…» и опрашивает
статистику раз в 5 с, пока в очереди есть задания, — иначе счётчики «застывали».

### 6.4 Перезапись, история версий и токены (2026-10-17)

- **Полная перезапись + история.** Успешный ответ заменяет поля `photo_qwen`
  целиком, но прежний результат (если было описание/клиент/бренд/категория)
  уходит в `photo_qwen_history` (`schema/036`): модель, время, токены, когда
  вытеснили и какая модель вытеснила. Так смена модели не стирает прежнее —
  результаты можно сравнить. Чтение: `GET /v1/photos/{id}/qwen-history`, в
  карточке фото — «История описаний».
- **Модель на провайдера.** У локальной Ollama и у облака свои ключи
  (`qwen_model_ollama` / `qwen_model_openai`), в UI модель видна и сохраняется
  сразу при выборе; смена провайдера больше не теряет выбор другого.
- **Токены облака.** `usage` из ответа пишется в
  `prompt/completion/total_tokens`; карточка «Распознавание» показывает расход
  и разбивку «какая модель дала описания».
- **Лимит запросов (429).** Облачный провайдер ограничивает частоту: запрос
  повторяется до 3 раз с паузой (5/10/20 с, `Retry-After` уважается, максимум
  60 с), после чего задание честно падает с сообщением про лимит тарифа.
  Настройки: `SCENE_QWEN_CLOUD_RETRIES`, `SCENE_QWEN_CLOUD_RETRY_DELAY`.
  Массовый прогон на 650 фото упёрся в 429 — облако годится для небольших
  порций, пока лимит тарифа не поднят.

### 6.5 Кроп кадра: замер и вывод (2026-10-17)

Идея владельца: щит занимает лишь часть кадра, и при лимите 1280 px ему мало
пикселей — значит, кроп должен помочь. Сделаны настройка и замерный стенд.

- **Настройка.** `qwen_crop` (`off` по умолчанию) и `qwen_crop_ratio` (0.6) в
  `app_settings`: `center` берёт центральную часть кадра до уменьшения, поэтому
  щит занимает больше пикселей. Меняется без перезапуска; без настройки
  поведение прежнее (весь кадр).
- **Стенд.** `scripts/qwen_crop_stand.py` прогоняет одни и те же фото в
  нескольких режимах и сравнивает поля с тем, что уже лежит в базе (эталон —
  принятые ранее значения), с прогревом модели перед замером, чтобы времена
  были сравнимы. Облачный провайдер требует явного `--cloud` (изображения
  уходят наружу), принудительный провайдер — `--provider`.
- **Замер** (`docs/qwen_crop_experiment.md`, 6 фото, `qwen3-vl:4b-instruct`):

  | Режим | клиент | бренд | категория | среднее время |
  |---|---|---|---|---|
  | весь кадр | 100 % | 100 % | 83 % | 2.0 с |
  | центр 60 % | 40 % | 40 % | 33 % | 1.9 с |

  **Вывод: кроп ухудшает распознавание** — обрезая края, мы убираем контекст
  окружения, по которому модель и определяет клиента/бренд. Поэтому по
  умолчанию кроп **выключен**; для другого корпуса (крупные щиты анфас) замер
  можно переиграть стендом на своих фото, не меняя код.

## 7. Массовое пересканирование и журнал истории

В «Техническом разделе → Распознавание» кнопка **«Пересканировать»** запускает
деструктивное обновление QWEN за явно выбранный период (`date_from`, `date_to`,
фильтр по дате загрузки или съёмки). Операция:

1. не запускается, пока в очереди есть активные `QWEN_PHOTO` (сначала нужно
   остановить распознавание);
2. выбирает фотографии периода;
3. в одной транзакции копирует все текущие строки `photo_qwen` выбранных фото
   в `photo_qwen_history` с `replaced_by_model = текущая модель`;
4. удаляет текущие строки `photo_qwen`, чтобы грид не показывал старое описание
   как актуальное;
5. ставит новые `QWEN_PHOTO` задания с зафиксированными текущими provider/model
   и пишет общий run в историю запусков.

API: `POST /api/v1/jobs/qwen/rescan`, scope `jobs:write`. Ответ содержит
`photos`, `archived`, `jobs`, `skipped`, `model`, `run_history_id`. Архив
хранится в `photo_qwen_history`; при сбое постановки очереди данные уже
сохранены в истории, повторный запуск возможен обычной кнопкой QWEN.

Текстовый журнал доступен:

- `GET /api/v1/qwen/history` — последние версии всех фото с полями клиента,
  бренда, категории, тегов, старой/новой модели; ответ содержит и готовый
  `text` для отображения.
- третьей колонкой в «Распознавании» справа от статистики;
- внизу раскрытой «Истории описаний» на карточке фото и в окне редактирования.

### 7.1 Редактируемые промпты и параллелизм (2026-10-21)

- Промпты вынесены в `app_settings`: `qwen_prompt` (полный кадр) и
  `qwen_crop_prompt` (кроп щита). Пустое значение = встроенный промпт.
  Редактируются в «Техническом разделе → Распознавание»; действующий и
  встроенный текст отдаёт `GET /v1/qwen/settings`
  (`prompt`, `default_prompt`, `crop_prompt`, `default_crop_prompt`), меняет
  `PUT` теми же полями. Перезапуск не нужен.
- Встроенный промпт кропа уже содержит только нужные поля (description,
  client, brand, category, tags) — погоды, людей и окружения там нет.
- **Ollama не параллелит qwen3vl**: `OLLAMA_NUM_PARALLEL=3` логирует
  `model architecture does not currently support parallel requests`. Замер:
  10 кропов — 16.4 с при c=1, 16.0 с при c=2, 15.9 с при c=3 (растёт только
  латентность). Поэтому `--parallel` у QWEN-воркера не даёт прироста.
  Подробности и расчёт токенов — [`ollama_parallel_bench.md`](ollama_parallel_bench.md).
- Облачные VLM для кропов — [`cloud_vlm_bench.md`](cloud_vlm_bench.md):
  самый дешёвый надёжный вариант ~9 ₽ на 1000 фото.
