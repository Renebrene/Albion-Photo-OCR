# HYBRID — Technical Architecture

## 1. Назначение HYBRID

HYBRID является вторым этапом распознавания после DINO.

HYBRID не выполняет самостоятельное распознавание изображений.

Его задача — получить сохранённые результаты DINO для полного DINO BATCH, проанализировать TOP-5 кандидатов и последовательность фотографий и сформировать окончательный вердикт по каждому `photo_id`.

Основной поток:

DINO
→ PostgreSQL DINO RESULTS
→ HYBRID
→ PostgreSQL HYBRID RESULTS

HYBRID не изменяет исходные фотографии.

---

## 2. Источник данных HYBRID

Единственным входом HYBRID является PostgreSQL.

HYBRID получает:

- `batch_id`;
- сведения о DINO BATCH;
- `photo_id`;
- соответствующий `dino_run_id`;
- TOP-1 … TOP-5;
- оценки кандидатов;
- `dino_score`;
- `dino_second_score`;
- `dino_margin`;
- другие данные DINO, сохранённые в PostgreSQL.

HYBRID не читает исходные фотографии.

HYBRID не использует `source_path` для распознавания.

HYBRID не запускает DINO повторно.

HYBRID не использует SUBFINGERPRINTS.

---

## 3. Связь HYBRID с DINO BATCH

Каждый запуск HYBRID относится к конкретному `dino_batches.batch_id`.

HYBRID не формирует собственный набор фотографий.

Набор фотографий определяется DINO BATCH.

Следовательно:

DINO `batch_id`
→ фиксированный набор `photo_id`
→ сохранённые DINO results
→ HYBRID RUN

HYBRID не добавляет и не удаляет фотографии из входного BATCH.

---

## 4. Условие запуска HYBRID

HYBRID может начать обработку только после того, как соответствующий DINO BATCH получил:

`status = 'DONE'`

Состояния:

- `PENDING` — HYBRID не запускается;
- `RUNNING` — HYBRID не запускается;
- `FAILED` — HYBRID не запускается;
- `DONE` — BATCH разрешён как вход HYBRID.

`DONE` означает, что все `dino_runs` данного BATCH успешно завершены.

Наличие отдельных завершённых DINO runs не является основанием для запуска HYBRID.

HYBRID не работает с частично завершённым DINO BATCH.

---

## 5. PostgreSQL как контрольная точка

PostgreSQL является источником истины для перехода:

DINO → HYBRID

Перед созданием HYBRID RUN система проверяет:

1. существует ли `batch_id`;
2. какой у BATCH `run_type`;
3. имеет ли BATCH статус `DONE`;
4. совпадает ли `total_count` с количеством фотографий BATCH;
5. совпадает ли `completed_count` с `total_count`;
6. отсутствуют ли `PENDING` или `RUNNING` DINO runs;
7. существует ли DINO результат для каждого `photo_id`.

Если хотя бы одно условие не выполнено, HYBRID RUN не начинает обработку.

---

## 6. HYBRID RUN

`HYBRID RUN` — отдельная сущность PostgreSQL, представляющая один запуск алгоритма HYBRID на одном завершённом DINO BATCH.

Каждый HYBRID RUN имеет собственный идентификатор:

`hybrid_run_id`

HYBRID RUN связан с:

- одним `dino_batch_id`;
- фиксированным набором DINO results этого BATCH.

Один DINO BATCH может иметь несколько HYBRID RUN.

Пример:

DINO BATCH #1
→ HYBRID RUN #1

DINO BATCH #1
→ HYBRID RUN #2

Оба HYBRID RUN используют одни и те же сохранённые DINO results.

---

## 7. Состояния HYBRID RUN

HYBRID RUN использует состояния:

- `PENDING`;
- `RUNNING`;
- `DONE`;
- `FAILED`.

Переход:

`PENDING → RUNNING → DONE`

или:

`PENDING → RUNNING → FAILED`

HYBRID RUN не переходит в `RUNNING`, если соответствующий DINO BATCH не имеет состояния `DONE`.

---

## 8. Фиксация входа HYBRID RUN

После создания HYBRID RUN его входом является конкретный `dino_batch_id`.

DINO BATCH после состояния `DONE` не изменяется.

Поэтому повторный запуск HYBRID на том же BATCH использует тот же набор DINO results.

HYBRID RUN не создаёт новый DINO BATCH.

HYBRID RUN не изменяет существующие `dino_runs`.

HYBRID RUN не изменяет `dino_candidates`.

---

## 9. Результат HYBRID

Для каждого обработанного `photo_id` HYBRID сохраняет отдельный результат.

Результат содержит как минимум:

- `photo_id`;
- `dino_batch_id`;
- `dino_run_id`;
- исходный лучший DINO кандидат;
- окончательный HYBRID кандидат;
- изменение решения;
- исходную оценку;
- итоговую оценку;
- итоговый margin;
- информацию о соседях;
- статус;
- время обработки;
- сообщение об ошибке при наличии.

Конкретная SQL-структура этих данных определяется отдельной схемой PostgreSQL.

---

## 10. История HYBRID

История HYBRID хранится отдельно от истории DINO.

DINO сохраняет свои `dino_runs`.

HYBRID сохраняет свои `hybrid_runs` и результаты каждого запуска.

Существующий HYBRID RUN не перезаписывается новым запуском.

Повторный запуск создаёт новый `hybrid_run_id`.

Это позволяет сравнивать результаты разных запусков HYBRID на одном и том же DINO BATCH.

---

## 11. Повторный запуск HYBRID

Завершённый DINO BATCH может использоваться повторно.

Повторный запуск HYBRID:

- использует тот же `dino_batch_id`;
- использует сохранённые DINO results;
- не запускает DINO;
- не читает исходные фотографии;
- создаёт новый `hybrid_run_id`;
- сохраняет новую историю результатов.

Таким образом:

DINO BATCH #1
→ HYBRID RUN #1
→ результаты

DINO BATCH #1
→ HYBRID RUN #2
→ результаты

DINO BATCH #1 остаётся неизменным.

---

## 12. FORCE_RERUN DINO

`FORCE_RERUN` относится к DINO, а не к HYBRID.

При FORCE_RERUN создаётся новый DINO BATCH и новые `dino_runs`.

После успешного завершения новый DINO BATCH получает:

`status = 'DONE'`

После этого он может стать входом отдельного HYBRID RUN.

Старый DINO BATCH при этом не изменяется.

---

## 13. Порядок обработки внутри HYBRID

HYBRID получает полный фиксированный набор фотографий конкретного DINO BATCH.

Последовательность фотографий определяется внутри этого BATCH.

Она используется для анализа соседей и серий.

HYBRID работает с сохранёнными TOP-5 DINO кандидатами.

Основной источник решения:

DINO TOP-5
+
анализ последовательности и соседей.

SUBFINGERPRINTS в новом HYBRID не используются.

---

## 14. Граница HYBRID → PREVIEW

После формирования окончательного HYBRID вердикта результат записывается в PostgreSQL.

PREVIEW является отдельным механизмом.

Он может использовать:

- `photo_id`;
- окончательный HYBRID ID;
- данные, необходимые для формирования отображения.

Цепочка:

DINO BATCH DONE
→ HYBRID RUN
→ HYBRID VERDICT в PostgreSQL
→ PREVIEW
→ GRID

PREVIEW не является частью HYBRID.

GRID не является частью HYBRID.

---

## 15. Основной принцип

PostgreSQL является источником истины для всех переходов между этапами.

DINO отвечает за получение первичного результата распознавания.

HYBRID отвечает за окончательный вердикт на основании сохранённых результатов DINO.

PREVIEW отвечает за подготовку отображения после появления HYBRID вердикта.

Ни один следующий этап не должен определять готовность предыдущего этапа по наличию файлов на диске.



## Корзина «Требуют проверки»: порог уверенности (2026-10-23)

Название корзины — «Требуют проверки»; этап после QWEN называется
«Уточнение» (docs/series_merge.md). Это разные вещи: корзина —
состояние фото, этап — автоматическое связывание серий.

Раньше фото получало адрес от гибрида при любом совпадении — даже когда оно
было совсем неявным. Теперь у распознавания есть нижний порог: если сходство
выбранного кандидата ниже него, адрес не присваивается, а фото попадает в
«Требуют проверки» — корзину для ручного разбора.

### Что такое уверенность

`dino_candidates.score` первого ранга того DINO-прогона, который породил
вердикт (`hybrid_results.dino_run_id`). Это доля сходства 0…1.

Взвешенная сумма самого гибрида (`hybrid_score`, на корпусе ~12) для порога не
годится: она растёт от числа кандидатов и от бонуса за согласие соседей, то
есть измеряет не уверенность, а «сколько всего нашлось».

### Порог

| | |
|---|---|
| Настройка | `app_settings.hybrid_low_score`, правится в «Техническом разделе → Сортировка» без перезапуска |
| Умолчание | 0.85 (`SCENE_HYBRID_LOW_SCORE`) |
| Выключить | значение 0 — адрес получает любое совпадение, как раньше |
| API | `GET /v1/hybrid/settings`, `PUT /v1/hybrid/settings` (`settings:write`) |

Порог применяется **при чтении**: данные не пересчитываются, поэтому значение
можно двигать и сразу видеть, сколько фото требует разбора.

Подбор значения: рядом с полем показан текущий размер корзины, а при вводе
нового значения — счётчик **до сохранения**
(`GET /v1/hybrid/settings/preview?low_score=…`, запросы сглажены). Так порог
подбирается по своему корпусу, а не наугад. Ориентир на текущих данных:

| Порог | В «Требуют проверки» |
|---|---:|
| 0.70 | 14 фото |
| 0.80 | 44 |
| 0.85 | 106 (умолчание) |
| 0.90 | 300 |
| 0.95 | 1131 |

Замер на корпусе 1518 фото (все с вердиктом): DINO-сходство выбранного
кандидата — минимум 0.514, у 5 % ниже 0.827, медиана 0.935. При пороге 0.85 в
корзину уходят 106 фото (7 %).

### Как это выглядит

- В панели адресов первой строкой идёт **«Требуют проверки»** со своим счётчиком —
  это не адрес, а корзина. Счётчик считается тем же условием распознавания и
  тем же периодом, что и адреса, поэтому сходится с фильтром.
- Фильтр `addr:review` показывает содержимое корзины. Важно: грид всегда
  запрашивает «только распознанные», а корзина — ровно те, кто не распознан,
  поэтому при выборе «Требуют проверки» фильтр распознавания не применяется (иначе
  страница была бы пустой).
- В плитке такое фото подписано «требует уточнения», в подсказке — уверенность.
- **Выход из корзины** — ручное переопределение адреса в карточке фото: оно
  побеждает автоматику, и фото возвращается в грид под нужным адресом.

### Что считается «не распознано»

- совпадение слабее порога;
- совпадения нет (вердикт есть, но `hybrid_final_id` пуст);
- вердикта нет вовсе (фото ещё не проходило DINO/HYBRID).

Последнее означает, что во время большого инспектирования корзина растёт вместе
с числом новых фото — это ожидаемо: они действительно ждут распознавания.

### Ограничения и риски

- Проверка добавляет подзапрос к `dino_candidates` на строку. На 1518 фото
  незаметно; при 57 000, если станет узким местом, уверенность материализуется
  колонкой в `hybrid_results` (миграция + backfill) — это отдельный шаг.
- Порог влияет и на статистику: счётчик распознанных адресов считается тем же
  условием, что и панель.
- Откат: `hybrid_low_score = 0` (или удалить строку настройки) — поведение
  возвращается к прежнему, ничего не теряется.

### Тесты

`tests/test_review_bucket.py`: правила и валидация порога, вид SQL при
включённом и выключенном пороге (без базы); на одноразовой базе — слабое
совпадение уходит из адреса, снижение порога возвращает его, порог 0 сохраняет
прежнее поведение, уверенность отдаётся в карточке фото, фото без совпадения
попадает в корзину с `confidence = NULL`.


## Серии кадров: одно имя, прочитанное по-разному (2026-10-23, анализ)

Фото снимают сериями с видеоэкранов: соседние кадры — обычно один и тот же
ролик, но кадр бывает неполным (надпись не успела появиться), смазанным или
перекрытым машиной. QWEN читает «Ян» вместо «Яндекс», и в базе появляются
разные клиент и бренд.

Разбор `scripts/series_check.py` (только чтение) на корпусе 1518 кадров:

- **Интервалы**: между соседними кадрами одного экрана медиана 41 с, 39 %
  в пределах 15 с, 46 % — в пределах 30 с. Дальше начинаются съёмки других
  дней (75-й процентиль — 8,8 суток).
- **Пар «одно имя прочитано по-разному»** внутри серий: 8 у клиента (11 фото)
  и 24 у бренда (59 фото). Примеры: `АКБ` → `АКБ на всё`, `АО «ТБАНК»` →
  `АО «ТБАНК», ООО «Чанъань Моторс Рус»`, `Ozon fresh` → `Ozon Fresh`,
  `билайн` → `Билайн`, `ГиперЛента` → `ГИПЕР ЛЕНТА`.
- **Ловушка**: по всей базе `Яндекс` — префикс `Яндекс Лавка`, `Яндекс Маркет`
  и `Яндекс.Еда`, но это **разные бренды**. Склеивать по префиксу глобально
  нельзя — только внутри серии, где рекламодатель один.

### Признак «тот же ролик» — описание, а не время

Время само по себе не различает ролики: видеоэкран крутит плейлист. Замер
согласия соседних кадров одного экрана (интервал ≤ 30 с) в зависимости от
похожести описаний QWEN (пересечение слов):

| Схожесть описаний | Пар | Клиент совпал | Бренд совпал |
|---|---:|---:|---:|
| ≥ 0.6 | 106 | 90 % | 87 % |
| 0.3–0.6 | 140 | 79 % | 82 % |
| < 0.3 | 416 | 56 % | **17 %** |

То есть при похожих описаниях соседи почти всегда про один ролик, при разных —
почти всегда про разные (бренд совпадает лишь в 17 % случаев). Отсюда правило
отбора: **тот же экран + интервал ≤ 30 с + схожесть описаний ≥ 0.6**.

### Что предлагается делать с такими группами

1. **Нормализация имён (безопасно)**: если внутри группы одно чтение —
   префикс, вариант написания или латиница/кириллица другого, предложить алиас
   `client_aliases` (короткое → полное). Это неразрушающая нормализация: сами
   результаты QWEN не перезаписываются, а фильтры, панели и статистика
   начинают считать варианты одним именем. Ровно так уже сделаны алиасы
   `Блавоёр → Благояр` и `AAA MOTORC → ААА МОТОРС`.
2. **Дополнение пустых полей (осторожно)**: если у кадра клиент или бренд не
   прочитан, а группа единодушна, подставить значение группы. Требовать
   единодушия обязательно: 10–13 % соседей даже при схожести ≥ 0.6 расходятся.
3. Автоматически применять **только** алиасы; подстановку — после просмотра
   оператором. Причина: цена ошибки выше выгоды, а объём (десятки фото)
   спокойно разбирается руками.

Порог схожести, интервал и список найденных пар видны в отчёте
`scripts/series_check.py`; он ничего не меняет.

### Карточка фото из «Требуют проверки»

Чтобы решать по факту, а не гадать, карточка показывает **что предложил
дино-гибрид по обычной схеме — без порога**: имя адреса и уверенность.

- В API это поля `suggested_address` (имя адреса предложенного слепка) и
  `suggested_fingerprint` (сам слепок); `confidence` — сходство кандидата.
  Они заполнены и для фото ниже порога, где `address` пуст.
- В плитке подсказка у подписи «требует проверки» содержит предложение и
  уверенность.
- В окне просмотра под именем файла выводится «Дино-гибрид предлагал: … ·
  уверенность …».
- Принять предложение — это обычное переопределение адреса в карточке; фото
  уходит из корзины и возвращается в грид под этим адресом.

Формулировки: **«Требуют проверки»** — корзина (состояние фото),
**«Уточнение»** — этап после QWEN (связывание серий, `docs/series_merge.md`).
