# Параллельные вызовы Ollama и стоимость токенов — 2026-10-21

Проверка на локальной машине (Ryzen 5 5600, 31 GB RAM, RTX 3060 12 GB),
модель `qwen3-vl:4b-instruct` (Q4_K_M, 3.5 GB), Ollama 0.40.0.

## Что измеряли

Десять кропов щитов из `scripts/cloud_vlm_crops.py`, рабочий промпт кропа,
`num_predict=768`, `temperature=0`, `format=json`. Два сервера Ollama:
основной (конфигурация по умолчанию) и временный на порту 11435 с
`OLLAMA_NUM_PARALLEL=3` (тот же GPU). После прогрева:

| режим | 10 кропов, с | с/фото | средняя латентность, с | макс., с |
|---|---:|---:|---:|---:|
| c=1 | 16.4 | 1.64 | 1.64 | 2.12 |
| c=2 | 16.0 | 1.60 | 3.04 | 3.88 |
| c=3 | 15.9 | 1.59 | 4.29 | 5.65 |

**Прироста нет.** Лог временного сервера прямо говорит:

```
model architecture does not currently support parallel requests
architecture=qwen3vl
```

Все запросы обслуживает один слот (`slot id 0`), они выполняются
последовательно; параллелизм только увеличивает ожидание каждого запроса.
Поэтому `scene-qwen-worker --parallel N` для QWEN не ускорит прогон — задания
будут стоять в очереди внутри Ollama.

## Из чего складывается время одного фото

По логам Ollama (тёплый запуск):

| часть | значение |
|---|---|
| вход | ~1245 токенов: 185 текста промпта + ~1060 изображения |
| prompt eval (первый раз) | ~800 мс на 1261 токен |
| prompt eval (кэш) | ~12 мс на 1 токен |
| выход | ~120 токенов |
| скорость генерации | 11.35 мс/токен ≈ **88 токенов/с** |
| итого на фото | ~1.3–1.6 с |
| в рабочем пайплайне | ~2.5 с (плюс чтение файла, кроп, БД, очередь) |

Вывод: **время почти поровну между кодированием картинки и генерацией
ответа**; генерация линейна по числу выходных токенов.

## Насколько можно сокращать токены

- **Текстовый промпт** — всего ~185 токенов (15 % входа); сокращать его
  бессмысленно, он уже содержит только нужные поля: description, client,
  brand, category, tags. Погоды, людей и окружения в промпте кропа нет
  вовсе — модель их не описывает.
- **Изображение** — ~1060 токенов (85 % входа). Уменьшение длинной стороны
  кропа с 2048 до 1280 px даёт примерно в 2.5 раза меньше image-токенов и
  ~0.4–0.6 с экономии, но мелкий текст на баннере может пострадать.
- **Выход** — ~120 токенов ≈ 1.4 с. Если ограничить description одной
  фразой (≤ 15–20 слов), а tags — пятью значениями, ответ сократится до
  ~60–70 токенов и фото станет быстрее примерно на 0.6–0.7 с (25–30 %).
- **Промпт редактируется без перезапуска**: «Технический раздел →
  Распознавание» → поля «Промпт для кропа щита» и «Промпт для полного
  кадра». Пустое поле или кнопка «Встроенный» возвращают стандарт.
  Настройки хранятся в `app_settings` (`qwen_crop_prompt`, `qwen_prompt`).

## Как всё-таки распараллелить

- **Ollama + qwen3vl** — нельзя (см. выше); ждать поддержки в новых версиях.
- **vLLM / llama.cpp server с continuous batching** — поддерживают
  параллельные запросы к VLM и на 3060 дают обычно 1.5–2.5× на пакете из
  десятков фото. Цена — отдельный сервер, совместимость формата Qwen3-VL и
  настройка (на Windows Server — через WSL2).
- **Несколько GPU/машин** — единственный способ масштабироваться линейно.
- **Не отправлять повторно уже известное**: кэш по эмбеддингу вырезки щита
  (тот же баннер → тот же рекламодатель) может убрать часть вызовов, но
  требует хранения эмбеддингов и проверки порога на реальных парах.

## Итог

- Параллелить вызовы Ollama для этой модели на одной RTX 3060 бессмысленно:
  1.6 с/фото и так близко к пределу одного слота.
- Реальный выигрыш — в сокращении выходных токенов (описание/теги) и,
  возможно, размера кропа; это 20–30 % без потери качества.
- Для пакетной обработки, где GPU занят, дешевле отдать кропы в облако:
  см. [`cloud_vlm_bench.md`](cloud_vlm_bench.md) — от 9 ₽ на 1000 фото.
