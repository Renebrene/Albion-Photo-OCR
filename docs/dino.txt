# DINO — Technical Architecture

## 1. Назначение

DINO — независимый этап распознавания фотографий.

DINO получает фотографии не из файловой системы напрямую как источник
очереди, а из PostgreSQL.

PostgreSQL является источником истины для состава работ:

- photo_id;
- source_path;
- физическая идентичность фотографии;
- состояние и результаты DINO.

Исходные фотографии остаются READ-ONLY.

---

## 2. Общая архитектура

ORIGINAL (READ-ONLY)
   |
   v
INGEST
   |
   v
PostgreSQL.photos
   |
   | photo_id + source_path
   v
DINO RUN / BATCH
   |
   +-------------------+
   |                   |
   v                   v
DINO workers        PostgreSQL
   |                   |
   | DINO v3.3         |
   |                   |
   +-------------------+
           |
           v
PostgreSQL.dino_runs
PostgreSQL.dino_candidates
           |
           v
        HYBRID
           |
           v
PostgreSQL HYBRID results

PREVIEW и GRID являются отдельными механизмами.

---

## 3. DINO RUN / BATCH

Каждый запуск DINO имеет собственный RUN.

RUN формируется как снимок набора фотографий, которые требуют
обработки на момент формирования batch.

После формирования batch его состав не изменяется.

Например:

DINO RUN #100
batch = 256 фотографий

Если во время выполнения INGEST добавляет ещё 30 фотографий:

DINO RUN #100 = прежние 256 фотографий

Новые 30 фотографий не добавляются в текущий RUN.

Они становятся кандидатами следующего DINO RUN.

---

## 4. Формирование batch

На момент запуска DINO PostgreSQL определяет фотографии,
для которых отсутствует успешный результат DINO.

Для каждой фотографии в batch передаются:

- photo_id;
- source_path.

DINO не ищет фотографии самостоятельно по каталогам
и не использует файловую систему для определения состава очереди.

После получения batch он распределяется между DINO workers.

При текущем оборудовании:

- CPU: Ryzen 5 5600;
- logical CPUs: 12;
- DINO workers: до 6.

Распределение фотографий между workers выполняется внутри DINO RUN.

---

## 5. Работа worker

Worker получает:

photo_id + source_path

Затем:

1. читает оригинальный файл по source_path;
2. выполняет существующий DINO v3.3 recognition core;
3. получает TOP-1 ... TOP-5;
4. получает scores и descriptor components;
5. вычисляет dino_score;
6. вычисляет dino_second_score;
7. вычисляет dino_margin;
8. определяет confidence/status;
9. записывает результат в PostgreSQL;
10. переходит к следующей фотографии своего batch.

Исходный файл не изменяется.

---

## 6. Запись результатов

Результат каждой фотографии записывается в PostgreSQL
сразу после завершения её обработки.

Не требуется ждать завершения всего RUN.

Для одной фотографии сохраняются:

dino_runs:

- run_id;
- photo_id;
- run_type;
- status;
- dino_best_id;
- dino_score;
- dino_second_score;
- dino_margin;
- dino_confidence;
- dino_status;
- started_at;
- finished_at;
- dino_time_sec;
- error_message.

dino_candidates:

- run_id;
- rank;
- fingerprint_id;
- score;
- global_score;
- environment_score;
- color_score;
- spatial_score;
- best_image;
- best_image_score.

Сохраняется TOP-5.

---

## 7. Состояние RUN и фотографии

Успешная обработка одной фотографии заканчивается состоянием:

RUNNING -> DONE

При ошибке:

RUNNING -> FAILED

Ошибка одной фотографии не должна останавливать обработку
остальных фотографий RUN.

Предыдущие успешные результаты не удаляются.

---

## 8. Новые фотографии во время RUN

INGEST может работать независимо от DINO.

Если во время:

DINO RUN #100

появились новые фотографии, они не изменяют состав
DINO RUN #100.

После завершения RUN PostgreSQL может показать наличие
новых фотографий, требующих DINO.

Для них создаётся следующий RUN.

Таким образом, каждый RUN имеет фиксированный состав,
а система в целом остаётся динамической.

---

## 9. FORCE RERUN

FORCE_RERUN является отдельным режимом DINO.

Он используется для повторной обработки фотографии,
у которой уже существует успешный DINO результат.

При FORCE_RERUN:

- предыдущий dino_runs не удаляется;
- создаётся новый run_id;
- новый запуск получает run_type = FORCE_RERUN;
- новый результат записывается отдельно.

Старый результат остаётся доступным для истории и сравнения.

---

## 10. Параллельность DINO и HYBRID

DINO и HYBRID являются независимыми вычислительными этапами.

DINO:

- использует GPU для DINO inference;
- использует до половины logical CPUs для worker processing.

HYBRID:

- работает независимо;
- использует CPU;
- использует до половины logical CPUs;
- не читает оригинальные фотографии;
- не запускает DINO повторно.

При текущем Ryzen 5 5600:

DINO   -> до 6 CPU workers
HYBRID -> до 6 CPU workers

---

## 11. Граница между DINO и HYBRID

DINO завершает свою работу записью результатов в PostgreSQL.

HYBRID получает входные данные из PostgreSQL:

- photo_id;
- DINO TOP-1 ... TOP-5;
- scores;
- margin;
- другие сохранённые DINO данные.

HYBRID не читает оригинальный файл.

HYBRID не выполняет повторный DINO inference.

HYBRID не использует SUBFINGERPRINTS.

HYBRID принимает собственный окончательный вердикт
и записывает его обратно в PostgreSQL.

---

## 12. Источник данных

Источник фотографий:

PostgreSQL.photos

Источник DINO результатов:

PostgreSQL.dino_runs
PostgreSQL.dino_candidates

Источник HYBRID входных данных:

PostgreSQL DINO results

PostgreSQL является центральным источником состояния
между вычислительными этапами.

---

## 13. Исходные файлы

Исходные фотографии:

/home/alexice/Desktop/test

используются только для чтения.

DINO не:

- переименовывает файлы;
- перемещает файлы;
- копирует файлы;
- удаляет файлы;
- создаёт производные изображения;
- изменяет содержимое оригиналов.

---

## 14. Архитектурный принцип

Система разделяет:

PHYSICAL IDENTITY

и

COMPUTATIONAL RESULTS.

INGEST отвечает за физическую идентичность фотографии
и создаёт photo_id.

DINO отвечает за результат визуального распознавания.

HYBRID отвечает за окончательный вердикт на основании
DINO результатов и последовательного контекста.

PREVIEW и GRID являются отдельным последующим механизмом.

---

## 15. Фиксированный состав DINO BATCH

Каждый запуск DINO создаёт отдельный BATCH.

После создания BATCH его состав фотографий фиксируется.

Для каждой фотографии, вошедшей в BATCH, PostgreSQL создаёт
отдельную запись `dino_runs` со статусом `PENDING`.

Таким образом:

BATCH
├── photo A → dino_run → PENDING
├── photo B → dino_run → PENDING
├── photo C → dino_run → PENDING
└── ...

Состав BATCH после создания не изменяется.

Фотографии, появившиеся в PostgreSQL.photos после создания
текущего BATCH, в текущий BATCH не добавляются.

Они попадут в следующий NORMAL BATCH.

Это обеспечивает фиксированный набор входных данных
для каждого запуска DINO.

---

## 16. NORMAL BATCH

NORMAL BATCH формируется из фотографий PostgreSQL.photos,
для которых ещё нет успешного DINO результата.

При создании NORMAL BATCH:

1. PostgreSQL определяет полный набор фотографий.
2. Количество фотографий фиксируется в `total_count`.
3. Для каждой фотографии создаётся `dino_runs`.
4. Каждый созданный run получает:
   - `batch_id`;
   - `photo_id`;
   - `run_type = NORMAL`;
   - `status = PENDING`.
5. После этого состав BATCH считается закрытым.

Новые фотографии, зарегистрированные INGEST после закрытия
BATCH, не влияют на его `total_count` и не добавляются в него.

---

## 17. Распределение BATCH между workers

После создания BATCH общее количество фотографий известно.

DINO использует до половины logical CPUs.

При текущем Ryzen 5 5600:

6 logical CPU workers.

Фотографии текущего BATCH распределяются между workers
из уже сформированного фиксированного набора.

Worker получает из PostgreSQL:

- run_id;
- photo_id;
- source_path.

Worker читает оригинальную фотографию по `source_path`,
выполняет DINO и сразу записывает результат в PostgreSQL.

Результаты не накапливаются до окончания всего BATCH.

---

## 18. Состояния DINO BATCH

BATCH использует состояния:

PENDING
↓
RUNNING
↓
DONE

или:

PENDING
↓
RUNNING
↓
FAILED

`total_count` фиксируется при создании BATCH.

`completed_count` увеличивается после успешного завершения
отдельного DINO run.

`failed_count` увеличивается после неуспешного DINO run.

BATCH считается DONE, когда все его runs завершены успешно.

При наличии завершённых с ошибкой runs BATCH получает состояние FAILED.

---

## 19. FORCE_RERUN BATCH

FORCE_RERUN предназначен для повторной обработки
явно выбранных фотографий.

FORCE_RERUN не изменяет и не удаляет предыдущий результат.

Для выбранного `photo_id` создаётся новый `dino_runs`:

- новый `run_id`;
- новый BATCH;
- `run_type = FORCE_RERUN`;
- `status = PENDING`.

Предыдущий успешный DINO run сохраняется.

Таким образом одна фотография может иметь несколько исторических
DINO runs.

Последний успешный результат определяется по новому завершённому run.

FORCE_RERUN не должен автоматически запускать повторную обработку
всех фотографий с существующим DONE результатом.

---

## 20. Новые фотографии во время DINO RUN

INGEST может продолжать регистрировать новые фотографии
во время выполнения DINO BATCH.

Это не изменяет текущий BATCH.

Пример:

BATCH #1 создан:

256 фотографий

Во время его выполнения INGEST зарегистрировал:

30 новых фотографий

Результат:

BATCH #1 → 256 фотографий
BATCH #2 → 30 новых фотографий

Новые фотографии не должны появляться внутри уже работающего
BATCH #1.

---

## 21. История запусков

PostgreSQL сохраняет историю DINO runs.

Один `photo_id` может иметь:

- NORMAL run;
- FORCE_RERUN run;
- несколько FORCE_RERUN runs.

Старые runs не удаляются при повторной обработке.

Это позволяет сохранять историю вычислений и сравнивать результаты
разных запусков.

---

## 22. PostgreSQL как источник состояния BATCH

Состояние BATCH не является только состоянием памяти процесса.

PostgreSQL хранит:

`dino_batches`

- batch_id;
- run_type;
- status;
- total_count;
- completed_count;
- failed_count;
- timestamps.

PostgreSQL хранит принадлежность каждого DINO run к BATCH:

`dino_runs.batch_id`.

Таким образом после перезапуска процесса можно определить:

- какие BATCH существуют;
- сколько фотографий было в каждом BATCH;
- какие runs завершены;
- какие runs завершились ошибкой;
- какие runs ещё ожидают обработки.


## 23. Граница DINO → HYBRID

HYBRID запускается не для отдельных фотографий и не для незавершённого DINO BATCH.

После создания DINO BATCH его состав фиксируется. DINO обрабатывает фотографии этого BATCH и записывает результаты в PostgreSQL по мере завершения каждой фотографии.

Для каждого фото результат DINO сохраняется в `dino_runs` и `dino_candidates` сразу после завершения обработки.

Когда все `dino_runs` данного BATCH завершены успешно, BATCH получает состояние `DONE`.

Только BATCH со статусом `DONE` становится входом для HYBRID.

Таким образом:

DINO BATCH → DINO results → BATCH DONE → HYBRID BATCH

HYBRID не начинает финализацию BATCH, пока DINO не завершил весь соответствующий BATCH.

## 24. HYBRID получает именно DINO BATCH

HYBRID получает результаты по конкретному `batch_id`.

Для каждого `dino_run` HYBRID использует:

- `photo_id`;
- TOP-1 … TOP-5;
- оценки кандидатов;
- `dino_score`;
- `dino_second_score`;
- `dino_margin`;
- другие сохранённые данные DINO, необходимые для Hybrid.

HYBRID не обращается к исходным фотографиям.

HYBRID не запускает DINO повторно.

HYBRID не выполняет собственное изображенное распознавание.

HYBRID не использует SUBFINGERPRINTS.

Последовательность фотографий для Hybrid определяется внутри зафиксированного набора BATCH. Это важно для использования соседей и серий.

Результат HYBRID записывается в PostgreSQL и связывается с соответствующим `photo_id` и DINO BATCH.

## 25. DINO и HYBRID работают как независимые этапы

DINO и HYBRID являются отдельными этапами обработки.

DINO:

- читает `photo_id` и `source_path` из PostgreSQL;
- читает исходную фотографию;
- выполняет DINO v3.3;
- записывает результат в PostgreSQL.

HYBRID:

- ждёт завершения соответствующего DINO BATCH;
- читает результаты DINO из PostgreSQL;
- анализирует TOP-5 и последовательность;
- формирует окончательный вердикт;
- записывает вердикт в PostgreSQL.

HYBRID не зависит от наличия исходного файла после того, как DINO результат сохранён.

Новые фотографии, поступившие через INGEST во время работы DINO BATCH, не изменяют этот BATCH и не передаются текущему HYBRID.

Они попадут в следующий DINO BATCH.

PREVIEW и GRID находятся после HYBRID и являются отдельным механизмом:

DINO BATCH DONE
→ HYBRID
→ PostgreSQL HYBRID VERDICT
→ PREVIEW
→ GRID

Появление вердикта HYBRID в PostgreSQL является условием для следующего механизма подготовки отображения, но PREVIEW не является частью DINO или HYBRID.

## 26. Готовность BATCH для HYBRID

Строгим условием передачи DINO BATCH в HYBRID является:

`dino_batches.status = 'DONE'`

HYBRID не имеет права начинать обработку BATCH, если его состояние:

- `PENDING`;
- `RUNNING`;
- `FAILED`.

Состояние `DONE` означает, что все `dino_runs`, принадлежащие этому BATCH, завершились успешно.

Следовательно, HYBRID всегда получает полный зафиксированный набор DINO результатов данного BATCH.

Наличие отдельных завершённых `dino_runs` внутри ещё работающего BATCH не является основанием для запуска HYBRID.

Если один или несколько DINO runs завершились с ошибкой, соответствующий BATCH не передаётся в HYBRID автоматически.

Такое разделение исключает ситуацию, когда HYBRID принимает решение по неполному набору фотографий и неполному соседнему контексту.

## 27. PostgreSQL как контрольная точка DINO → HYBRID

PostgreSQL является источником истины для определения готовности BATCH.

HYBRID перед началом работы проверяет:

1. существование `batch_id`;
2. `run_type`;
3. `status = 'DONE'`;
4. `total_count`;
5. `completed_count`;
6. отсутствие незавершённых `dino_runs`;
7. наличие DINO результата для каждого фото BATCH.

После успешной проверки HYBRID получает фиксированный набор `photo_id` и DINO результатов, относящийся именно к этому BATCH.

HYBRID не определяет готовность BATCH по количеству файлов на диске и не обращается к исходным фотографиям для проверки состояния DINO.

Если BATCH не готов, HYBRID не начинает его обработку.

## 28. Повторный запуск HYBRID

DINO BATCH и HYBRID являются независимыми этапами.

Завершённый DINO BATCH не изменяется после получения состояния `DONE`.

При необходимости HYBRID может быть запущен повторно на том же `batch_id`, используя сохранённые DINO результаты PostgreSQL.

Повторный запуск HYBRID не требует повторного запуска DINO и не требует повторного чтения исходных фотографий.

История результатов HYBRID должна сохраняться отдельно от DINO runs.

FORCE_RERUN DINO создаёт новый DINO BATCH и новый набор `dino_runs`. Такой новый BATCH после состояния `DONE` может стать отдельным входом HYBRID.


## 29. Замеры CPU-параллелизма (2026-10-13)

Набор: 8 временных probe-фото (реальные результаты корпуса не изменялись),
CPU-only путь, модель `facebook/dinov2-base`, 12 логических CPU.

| workers | wall (весь batch) | per-item avg |
|---|---|---|
| 1 | 3.78–4.21 s | 0.32 s |
| 4 | 2.66 s | 0.74 s |
| 8 | 2.56 s | 1.39 s |

Выводы:

- Потоки почти не дают wall-clock выигрыша (упор в CPU/GIL) и заметно
  увеличивают время на фото из-за oversubscription.
- Значимая фиксированная часть бюджетa — загрузка модели (~2.5 s на batch),
  не параллелится потоками.
- Поэтому число воркеров вынесено в `SCENE_DINO_WORKERS` с дефолтом **1**
  (`0` = автоматически, половина CPU — для экспериментов); технически
  runner CPU-only.
- Реальный резерв ускорения — CUDA (GPU в системе есть, но runner принудительно
  использует CPU) и батчирование нескольких изображений в один forward
  (сейчас inference идёт по одному изображению на вызов). Это отдельная задача,
  требующая проверки эквивалентности результатов.

## 30. Исторические замеры (архив 111/) и решение по CPU/GPU

Из `111/chat_chunks/chunk_132.md` и `111/final_tz/summary_014.md`:

- Легаси, **DINO на CPU**: ≈ **0.488 с/фото**.
- Легаси, **DINO на GPU** (RTX 3060, 526 фото): **189.76 с** = **0.361 с/фото**;
  повторный прогон — 272.92 с (0.519 с/фото), при загрузке GPU ~6% и VRAM ~1.5 ГБ.
  То есть большая часть времени уходила не в inference, а в окружение
  (открытие JPEG, подготовка кадра, CPU-дескрипторы, сравнение).
- Архитектурное решение легаси: **DINO на CPU, Qwen — на GPU**, чтобы не
  конфликтовать за ресурсы.

Вывод: разница CPU/GPU по DINO умеренная, и она дополнительно «съедается»
совместной работой с QWEN на GPU. Поэтому текущий runner остаётся CPU-only
(это осознанное решение), а не переводится на CUDA.

Наши замеры (2026-10-13, probe-набор, workers=1): per-item ≈ **0.32 с** —
согласуется с легаси-CPU.

Батчирование (batch>1) в архиве обсуждалось, но **подтверждённых замеров в
найденных материалах нет** — числа там приведены как примеры-гипотезы. Это
отдельный эксперимент (см. следующий раздел при реализации).

## 31. Батчирование DINO (2026-10-13)

Добавлен батч-путь (`SCENE_DINO_BATCH`, `run_batch(..., batch_size=...)`,
`--batch`): несколько изображений уходят в один forward, дескрипторы и
сравнение считаются на каждое фото как раньше. Батч-путь работает при
`workers=1`; при ошибке чанк автоматически разбирается по одному.

Замер (8 probe-фото, CPU, workers=1):

| batch | wall (весь batch) |
|---|---|
| 1 | 4.02 s |
| 4 | 3.26 s |
| 8 | 3.30 s |

**Эквивалентность проверена:** для batch 4 и 8 `dino_best_id` совпадает с
batch=1, а `dino_score` — в пределах 1e-6. То есть батчирование не меняет
результат распознавания.

Вывод: выигрыш умеренный (~19% wall на малом наборе; значимая часть — загрузка
модели), но сам compute-участок ускоряется примерно вдвое. Дефолт оставлен
`1` (поведение не меняется); `4–8` можно включать на больших корпусах.
