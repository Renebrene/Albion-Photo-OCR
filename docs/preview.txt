PREVIEW MAKER
=============

1. НАЗНАЧЕНИЕ

PREVIEW Maker — отдельный CPU-процессный слой pipeline, который после регистрации фотографии создаёт производные изображения для последующего отображения. Фото PREVIEW job ставится в отдельную PostgreSQL queue сразу после успешной регистрации, а не ждёт DINO, HYBRID или QWEN. Выделенный `scene-preview-worker` запускает существующий `ProcessPoolExecutor` (`SCENE_PREVIEW_WORKERS`, по умолчанию половина логических CPU-ядер).

PREVIEW Maker НЕ выполняет распознавание сцены, НЕ определяет адрес и НЕ принимает решений DINO/HYBRID.

Архитектурная цепочка:

ORIGINAL PHOTO
      |
    INSPECT
      |
 PhotoRecord
      |
 PREVIEW MAKER
   |       |
 SMALL   MIDDLE
      |
 VALIDATION
      |
 PostgreSQL


2. ВХОДНОЙ КОНТРАКТ

PREVIEW Maker принимает только уже зарегистрированные объекты PhotoRecord, сформированные модулем INSPECT.

PhotoRecord содержит:

- photo_id
- source_path
- filename
- sha256
- container_format
- frame_count
- width
- height

PREVIEW Maker НЕ выполняет самостоятельный поиск исходных файлов и НЕ создаёт photo_id.

Создание PREVIEW без зарегистрированного photo_id не является допустимым штатным сценарием.

Правильный поток:

INSPECT
  |
photo_id
  |
PREVIEW Maker

НЕПРАВИЛЬНЫЙ поток:

filesystem
  |
PREVIEW Maker
  |
photo_id


3. РАБОТА С ИСХОДНЫМ ФАЙЛОМ

Исходные фотографии являются READ-ONLY источником.

PREVIEW Maker:

- не изменяет оригинал;
- не переименовывает оригинал;
- не перемещает оригинал;
- не создаёт производные файлы рядом с оригиналом.

Правила визуального источника:

MPO -> используется только frame 0.
JPEG -> используется исходное изображение.

Frame 0 используется только как визуальный источник для создания производных preview.


4. PREVIEW-ФАЙЛЫ

Для каждого photo_id создаются два preview:

PREVIEW_ROOT/
  small/
    PH_xxx.jpg
  middle/
    PH_xxx.jpg

Формат обоих preview:

JPEG

Имена файлов определяются исключительно photo_id.


5. РАЗМЕРЫ

Размеры preview не являются частью алгоритма распознавания и не должны быть захардкожены в коде.

Настройки:

SCENE_PREVIEW_ROOT
SCENE_PREVIEW_SMALL_SIZE
SCENE_PREVIEW_MIDDLE_SIZE
SCENE_PREVIEW_WORKERS

Текущие значения по умолчанию:

PREVIEW_ROOT = data/preview
SMALL = 320
MIDDLE = 1280
WORKERS = automatic

Размер задаётся как максимальная длина большей стороны.

Соотношение сторон исходного изображения сохраняется.

Если исходное изображение меньше заданного максимального размера, оно не увеличивается.


6. ПОЛИТИКА ОБРАБОТКИ

Для каждого preview:

preview существует?
  |
  +-- НЕТ ------> CREATE
  |
  +-- ДА
       |
       +-- VALID ------> SKIP
       |
       +-- INVALID ----> REGENERATE

Возможные действия:

CREATE
SKIP
REGENERATE
ERROR

CREATE:
Файл отсутствует. Создаётся новый preview.

SKIP:
Preview существует и успешно проходит полную проверку. Файл не перезаписывается.

REGENERATE:
Preview существует, но не проходит проверку. Создаётся заново.

ERROR:
Preview не удалось создать или проверить.


7. ВАЛИДАЦИЯ

Preview считается валидным только после проверки.

Проверяется:

1. существование файла;
2. что путь является обычным файлом;
3. формат JPEG;
4. Image.verify();
5. повторное открытие файла;
6. полный image.load().

Валидатор также поддерживает проверку ожидаемых размеров.

До успешной валидации preview не считается готовым.


8. НЕЗАВИСИМОСТЬ SMALL И MIDDLE

Порядок — MIDDLE, затем SMALL: MIDDLE нужен DINO как вход, и он должен
появиться первым. Исходник декодируется один раз: MIDDLE уменьшается из
оригинала, SMALL — уже из MIDDLE. Если MIDDLE уже валиден, а SMALL нет,
для SMALL открывается только файл MIDDLE (1280 px), оригинал не читается.
Замер на 10 фото: 0.432 → 0.293 с на фото.

Результаты SMALL и MIDDLE по-прежнему независимы: действие, ошибка и
валидность у каждого свои.

Пример:

SMALL  -> REGENERATE -> VALID
MIDDLE -> SKIP       -> VALID

В этом случае MIDDLE не пересоздаётся.

Если:

SMALL  -> VALID
MIDDLE -> ERROR

весь результат фотографии НЕ считается READY.


9. POSTGRESQL

Для preview используется отдельная таблица:

photo_previews

Preview-поля не добавляются непосредственно в таблицу photos.

Структура:

photo_previews
  - photo_id
  - small_path
  - middle_path
  - small_width
  - small_height
  - middle_width
  - middle_height
  - small_created_at
  - middle_created_at

photo_id является:

- PRIMARY KEY;
- FOREIGN KEY на photos(photo_id).

Связь:

photos
  |
  +-- photo_id
          |
          v
    photo_previews

Используется ON DELETE CASCADE.

Поэтому запись preview не может существовать в PostgreSQL без соответствующей зарегистрированной фотографии.


10. ИСТОЧНИК ИСТИНЫ

PREVIEW Maker не использует наличие файла в PREVIEW_ROOT как источник регистрации фотографии.

Принадлежность preview определяется через photo_id, полученный от INSPECT.

Нормальный поток:

SOURCE FILE
    |
  INSPECT
    |
PhotoRecord
    |
 photo_id
    |
PREVIEW Maker
    |
photo_previews

Наличие preview-файла без соответствующей регистрации не является штатным входом PREVIEW Maker.

Диагностика возможных orphan-файлов, если когда-либо понадобится, должна быть отдельной consistency/audit функцией и не должна смешиваться с генерацией preview.


11. POSTGRESQL UPDATE

PostgreSQL обновляется только после того, как оба preview успешно прошли валидацию.

SMALL valid
     +
MIDDLE valid
     |
    READY
     |
PostgreSQL UPSERT

Невалидный или отсутствующий preview не должен регистрироваться как готовый.


12. ПАРАЛЛЕЛИЗМ

PREVIEW Maker поддерживает параллельную обработку фотографий через ProcessPoolExecutor.

По умолчанию используется проектная политика:

workers = половина доступных logical CPU.

Для текущего оборудования:

logical CPU = 12
workers = 6

Явное значение SCENE_PREVIEW_WORKERS имеет приоритет.

Значение 0 означает автоматический режим.


13. ОТВЕТСТВЕННОСТЬ PREVIEW MAKER

PREVIEW Maker отвечает только за:

- получение уже зарегистрированного PhotoRecord;
- чтение исходного изображения;
- выбор визуального источника;
- создание SMALL;
- создание MIDDLE;
- сохранение JPEG;
- валидацию preview;
- формирование результата;
- регистрацию готовых preview в PostgreSQL.


14. ЧТО PREVIEW MAKER НЕ ДЕЛАЕТ

PREVIEW Maker НЕ:

- создаёт photo_id;
- регистрирует исходную фотографию;
- изменяет оригинал;
- перемещает оригинал;
- определяет адрес;
- определяет клиента;
- выполняет DINO;
- выполняет HYBRID;
- принимает решение о соответствии фотографии адресу;
- формирует результат распознавания.

Эти функции относятся к другим слоям pipeline.


15. СВЯЗЬ С DINO / HYBRID

PREVIEW не зависит от результата распознавания.

Общая архитектура:

                         +--> PHOTO_PREVIEW queue -> CPU workers
                         |                              |
                         |                           SMALL / MIDDLE
                         |                              |
ORIGINAL -> INSPECT ------+------------------------------+--> grid image ready
                         |
                         +--> DINO -> HYBRID -> address / recognition metadata
                                                   |
                                                   +--> grid recognition data

PREVIEW создаётся независимо от назначения адреса.

Наличие preview само по себе не означает, что фотография распознана.

GRID использует SMALL preview для изображения плитки; поля распознавания/address могут заполниться позже отдельным DINO/HYBRID pipeline. Само наличие preview не означает, что адрес уже распознан. API списка фото опирается на registered `photos`, а не на наличие `photo_previews`.

Актуальная очередь выполнения: после успешного commit новой строки `public.photos` INSPECT ставит `PHOTO_PREVIEW` job с одним `photo_id`. Synchronous upload использует тот же принцип. API request не генерирует изображения. `scene-preview-worker.service` claim-ит только `PHOTO_PREVIEW`; обычный worker по умолчанию исключает этот тип, поэтому старые DINO/QWEN jobs в общей FIFO queue его не задерживают. Внутри одного preview job вызывается существующий `ProcessPoolExecutor`; число CPU процессов задаётся `SCENE_PREVIEW_WORKERS` (0/по умолчанию — половина логических CPU). Запускается один queue poller, не несколько вложенных half-CPU pools.

Активные preview jobs атомарно дедуплицируются PostgreSQL partial unique index по `photo_id`. FAILED/CANCELLED jobs остаются историей и могут быть поставлены заново; генератор повторно валидирует и пропускает уже готовые SMALL/MIDDLE. Сбой постановки job не отменяет регистрацию фото, но отражается в ingest summary/upload result. Пропущенные (например, зарегистрированные до внедрения очереди) фото можно планово ставить ограниченными порциями через `POST /v1/previews/backfill?limit=500` (scope `jobs:write`, максимум 5000 за вызов).

PREVIEW file и DB row появляются после успешной валидации обоих размеров. До этого grid tile показывает skeleton/ошибку image load; PREVIEW не меняет recognition/address gating списка фото и не запускает DINO/HYBRID/QWEN. Схема/029 должна применяться до включения enqueue-кода и preview unit; миграцию не запускать на рабочей БД без согласованного rollout.


16. ПРОВЕРЕННЫЙ РЕЗУЛЬТАТ

PREVIEW pipeline проверен на полном тестовом наборе:

INPUT RECORDS: 256
TOTAL: 256
READY: 256
ERRORS: 0
DATABASE UPDATED: 256

Для 256 фотографий:

SMALL:
  CREATE: 255
  SKIP: 1

MIDDLE:
  CREATE: 255
  SKIP: 1

Также отдельно проверены:

- создание preview;
- повторный запуск с SKIP;
- повреждение preview с последующим REGENERATE;
- MPO -> frame 0;
- JPEG -> исходное изображение;
- валидация JPEG;
- PostgreSQL UPSERT / чтение;
- автоматическое определение 6 workers;
- полный запуск на 256 зарегистрированных фотографиях.

Итог:

INSPECT -> photo_id -> PREVIEW -> validation -> PostgreSQL

подтверждён на всём тестовом наборе.

Замер и рекомендации — `docs/preview_experiment_20261022.md`: q85 даёт
примерно −20 % веса MIDDLE без изменения разрешения.


## Потеря превью и недоступный оригинал (2026-10-22)

Производные файлы могут исчезнуть независимо от базы: перенос
`SCENE_PREVIEW_ROOT` на другой том, очистка производных, удаление каталога
руками. Запись фото при этом остаётся, и превью восстанавливается **по
`photo_id`** — рабочая папка с исходниками для этого не нужна.

### Пересоздание по photo_id

Путь к оригиналу берётся из `public.photos.source_path`, целевые файлы — из
детерминированных путей `build_preview_paths(SCENE_PREVIEW_ROOT, photo_id)`.
Поэтому восстановление не зависит от того, доступна ли папка из UI.

| Способ | Что делает |
|---|---|
| Кнопка **«Пересоздать превью»** во вкладке «Технический раздел → Инспектор» | ставит `PHOTO_PREVIEW` для фото без файлов (до 500 за раз) |
| `POST /api/v1/previews/backfill?limit=N` | то же по всей базе (прежнее поведение) |
| `POST /api/v1/previews/backfill` с телом `{"photo_ids": [...]}` | только указанные фото (пересоздание по `photo_id`) |
| `scripts/rebuild_previews.py` | то же из консоли: `--dry-run`, `--json`, `--limit`, `--photo-id` |

Общие правила:

- пересоздаются только те фото, у которых SMALL/MIDDLE отсутствуют или пусты;
  уже готовые файлы не перезаписываются;
- повторная постановка при активном задании не создаёт дубль (частичный
  уникальный индекс очереди);
- для одного фото задания не дублируются, повторный запуск безопасен.

### Если оригинала нет

Перед постановкой задания проверяется доступность оригинала: том смонтирован,
файл на месте, путь внутри `SCENE_ORIGINALS_ROOTS`. Фото с недоступным
оригиналом **не изменяется и не удаляется** — ни запись, ни превью; оно
попадает в счётчик `originals_missing` (в API, скрипте и в сообщении кнопки).
Это осознанное решение: потерянный файл — повод вернуть том или восстановить
файл из бэкапа, а не чистить базу.

Статус виден пользователю **до** нажатия «посмотреть/скачать»:
`GET /api/v1/photos/{photo_id}/original/status` → `{photo_id, available,
reason}`, где `reason` ∈ `ok` / `missing` / `outside_roots` /
`root_unavailable` / `not_configured`. Путь и имя файла наружу не отдаются.

`missing` и `root_unavailable` — разные состояния, и это важно на практике
(случай 2026-10-27). Если путь лежит внутри настроенного корня, а самого
каталога корня нет на машине (том отмонтирован, корпус переехал, диск не
подключили после перезагрузки), это `root_unavailable`, а не «файл не найден»:
иначе целый отмонтированный том выглядит как пропавшие файлы. Причина не
зависит от порядка корней — если путь попадает и в мёртвый, и в живой корень,
побеждает живой. Если мёртвый корень убрать из `SCENE_ORIGINALS_ROOTS`, тот же
путь станет `outside_roots`: тоже корректно, но сообщение будет другим
(разбор случаев — `docs/deployment.md` §3.1).

В гриде статус запрашивается при открытии фото; если оригинал недоступен:

- в окне просмотра появляется предупреждение «Оригинал недоступен (<причина>).
  Используйте превью — запись фото и его данные не удалены». Там же сказано,
  что чинит ситуацию: перенос путей `scripts/remap_source_root.py`
  («Переезд корпуса», `docs/deployment.md` §3.1) или бэкап. Повторная
  инспекция папки путь **не** исправляет — ingest вставляет записи с
  `ON CONFLICT DO NOTHING` и `source_path` существующей записи не переписывает
  (`docs/ingest.md`);
- рядом с «Исходный каталог» в карточке видно том, из которого запись
  (`Том: TEST`), а при `root_unavailable` — пометку «не подключён». Том — это
  только последний компонент пути корня (поле `source_root` в ответе API), сам
  путь наружу не уходит;
- кнопки «Открыть оригинал» и «Сохранить оригинал» выключены с подсказкой
  причины;
- превью (SMALL/MIDDLE) продолжает отдаваться как обычно;
- групповая выгрузка не останавливается на одном потерянном файле: такое фото
  пропускается и попадает в итоговое сообщение.

Ошибка самой проверки (сервер недоступен) кнопки **не** блокирует: отказ
покажет обычная загрузка, чтобы временный сбой не выглядел как пропавший файл.

### Отчёт по всему корпусу

```bash
# сколько оригиналов пропало (только чтение, ничего не меняет)
.venv/bin/python scripts/check_originals.py --json
# код возврата 1, если есть недоступные оригиналы; 2 — не задан SCENE_ORIGINALS_ROOTS
```

Пригодится перед переездом хранилища и как регулярная проверка на сервере с
сетевым томом. В отчёте четыре счётчика: `available`, `missing`,
`outside_roots`, `root_unavailable` — последний отдельно, чтобы отмонтированный
том не считался пропавшими файлами; код возврата 1 при любом из трёх.
Результат не сохраняется в базе: колонок вроде `original_missing_at` пока нет,
проверка делается по запросу (вариант без миграции).

### Сводка в техническом разделе

«Данные» → «Доступность оригиналов»: `GET /api/v1/originals/health` отдаёт по
каждому корню из `SCENE_ORIGINALS_ROOTS` путь, метку (`label` — последний
компонент корня), состояние каталога и число ссылающихся фото, плюс итоги
`total_photos`, `outside_roots` и `unavailable_roots`. Внутри — `is_dir()` по
самим корням и по одному `count(*)` на корень (`starts_with`, без `LIKE`),
поэтому запрос можно выполнять прямо в обработчике: на 57 тыс. записей это доли
секунды. Перебора файлов здесь нет — полная пофайловая проверка остаётся за
`scripts/check_originals.py`. Абсолютные пути корней в ответе есть: это тот же
технический раздел, где такие же пути показывает «Бэкапы» (scope `read`).

Поводом была реальная авария (2026-10-27): том Win10 отключили, 27 974 фото
ссылались на пути этого тома, и по одной карточке невозможно было понять, что
дело в диске. Панель показывает это одной строкой — «Win10 · не подключён ·
27 974». Совет про перенос путей она даёт только для отключённых корней, на
которых что-то есть: пустой корень в списке сам по себе никому не мешает.

### Тесты

`tests/test_original_availability.py` — классификация статуса (файл есть,
файл удалён, путь вне корней, корни не заданы, каталог вместо файла,
отсутствующий корень и корень-файл как `root_unavailable`, живой корень важнее
мёртвого, метка тома без абсолютного пути), пропуск
готовых превью, пропуск и подсчёт фото с недоступным оригиналом, лимит, ответ
маршрута без пути, 404 на неизвестное фото, проверка аргументов скриптов.
`tests/test_photo_preview_api.py` — тело `{"photo_ids": [...]}` и пустой список.
`tests/test_api_originals.py` — сводка по корням с подменённым соединением:
отключённый том отдельно от подключённого, подсчёт по префиксу пути, пустой
`SCENE_ORIGINALS_ROOTS` без обращения к базе, ответ маршрута.
`frontend/tests/originals-module.spec.js` — таблица корней, строка про
отключённый том с фото, молчание про пустой отключённый корень, сообщение при
пустом `SCENE_ORIGINALS_ROOTS`, видимая ошибка запроса.
`frontend/tests/photos-original-status.spec.js` — предупреждение вместо ошибки,
отдельный текст для неподключённого тома, подсказка про перенос путей вместо
прежней неверной про инспекцию, метка тома в карточке, поздний ответ
предыдущего фото, отсутствие блокировки при сбое проверки.
`frontend/tests/ingest-folder.spec.js` — запуск пересоздания и предупреждение
про недоступные оригиналы.


## Формат файлов превью: WebP (2026-10-22)

Превью пишутся в формате `SCENE_PREVIEW_FORMAT`: **по умолчанию `webp`**,
`jpeg` возвращает прежнее поведение. Замер и решение —
`docs/preview_experiment_20261022.md`: при том же разрешении 1280 px WebP q80
дал −46 % веса (291,5 КБ → 156,3 КБ на кадр), визуальных отличий на кропах
1:1 не найдено.

- Расширение пути следует формату: `small/<photo_id>.webp`,
  `middle/<photo_id>.webp`. Путь строится в `build_preview_paths()`;
  `app/preview/formats.py` — единственное место, где это задано.
- Качество: `SCENE_PREVIEW_QUALITY`, если задан; иначе умолчание формата
  (webp 80, jpeg 90). Настройки применяются к новым и пересоздаваемым файлам.
- **Переходный период безопасен.** API отдаёт файл с MIME по расширению и
  ищет его в порядке: текущий формат → прежний JPEG. Фото, которое ещё не
  пересоздано, продолжает показываться (никаких 404). QWEN выбирает вход
  (`analysis_input`) тем же правилом. Валидатор принимает JPEG и WebP,
  остальные форматы (например PNG) по-прежнему отклоняет.
- **Видео-постеры и производные** (кропы, сториборды, транскоды) остаются
  JPEG: на них формат превью не распространяется.

### Переход на новый формат в существующем корпусе

```bash
# 1. Пересоздать превью по photo_id (папка не сканируется)
.venv/bin/python scripts/rebuild_previews.py --dry-run
.venv/bin/python scripts/rebuild_previews.py --limit 5000

# 2. Убедиться, что у всех фото есть файл нового формата
.venv/bin/python scripts/rebuild_previews.py --dry-run

# 3. Убрать прежние JPEG (удаляются только те, рядом с которыми уже есть WebP)
.venv/bin/python scripts/rebuild_previews.py --purge-legacy --dry-run
.venv/bin/python scripts/rebuild_previews.py --purge-legacy
```

`--purge-legacy` затрагивает только `small/` и `middle/` внутри
`SCENE_PREVIEW_ROOT`; каталог `videos/` и производные файлы не трогаются.
Предел одного запуска — 20 000 файлов; файл без замены остаётся на месте и
попадает в счётчик `kept_without_replacement`.

После смены `SCENE_PREVIEW_FORMAT` нужно перезапустить API и preview-воркер:
значение читается при старте процесса. Схему БД менять не нужно — формат не
хранится в таблицах, путь и MIME выводятся из настройки.
