# Превью: вес и влияние сжатия/разрешения (2026-10-22)

Замер на 583 фото текущего корпуса и на 20 исходниках `test/*.JPG`
(средний исходник ~4,3 МБ).

## Что лежит сейчас

| Файл | Размер стороны | Средний вес | Всего на 583 | Прогноз на 57 000 |
|---|---:|---:|---:|---:|
| SMALL | 320 px | **23 КБ** | 13 МБ | **1,3 ГБ** |
| MIDDLE | 1280 px | **292 КБ** | 166 МБ | **16,6 ГБ** |
| видео-постеры | — | 47 КБ | 0,8 МБ | зависит от видео |

Итого превью на 57k: **≈18 ГБ**; почти всё — MIDDLE, потому что SMALL
используется только в плитках грида.

## Рекомендация

1. **SMALL оставить 320 px.** В плитках грида он уже используется на пределе;
   256 px даёт мизерную экономию (≈0,26 ГБ на 57k), но заметно мылит
   превью на экранах с высокой плотностью.
2. **MIDDLE перевести на q85 при 1280 px.** Это −21 % (≈3,5 ГБ на 57k) без
   изменения разрешения. Риск для QWEN минимален: кроп щита по-прежнему
   режется из оригинала; MIDDLE используется только как fallback, когда
   щит не найден (≈8 % фото).
3. **Разрешение MIDDLE не уменьшать до 1024 без отдельного замера.** Экономия
   ещё ≈4,5 ГБ, но fallback-кадры QWEN могут потерять мелкий текст. Если
   уменьшать, то сначала прогнать 50–100 fallback-фото и сравнить поля
   QWEN с текущими.
4. **Управление без правки кода:** `SCENE_PREVIEW_QUALITY` (по умолчанию 90).
   Уже существующие превью не перезаписываются; новый параметр действует
   на новые/пересоздаваемые файлы.

## Как проверить на своём корпусе

```bash
# текущее распределение
find data/preview/small -type f -printf '%s\n' | awk '{s+=$1;n++} END {print n, s/n}'
find data/preview/middle -type f -printf '%s\n' | awk '{s+=$1;n++} END {print n, s/n}'
```

Для смены качества на новых фото:

```ini
SCENE_PREVIEW_QUALITY=85
```

Перезапустить `scene-preview-worker`. Существующие 583 превью останутся
q90, пока их не пересоздать (например, при полном сбросе и повторном
инспектировании).

## Решение: WebP q80 (2026-10-22, выполнено)

Замер выше показал, что разрешение уменьшать невыгодно (MIDDLE 1280 совпадает
с окном просмотра/редактирования при retina), а качество и формат — да.
Отдельный замер форматов на 24 реальных оригиналах:

| Вариант MIDDLE 1280 | Средний вес | Δ к текущему | Кодирование |
|---|---:|---:|---:|
| JPEG q90 (как было) | 294 КБ | — | 7 мс |
| JPEG q85 | 235 КБ | −20 % | 6 мс |
| **WebP q85** | 193 КБ | −34 % | 82 мс |
| **WebP q80 (выбрано)** | **158 КБ** | **−46 %** | 77 мс |
| AVIF q60 | 111 КБ | −62 % | 160 мс |

WebP 320 px: JPEG q90 23,0 КБ → WebP q80 15,8 КБ (−31 %).

Выбран **WebP q80**: экономия как у AVIF минус половина, кодирование в два раза
быстрее и полная поддержка браузеров без оговорок. Прибавка CPU на 57 000
фото — около 70 минут суммарно, размазанных по preview-воркеру.

Визуальная проверка: кропы 1:1 (600×400) одних и тех же кадров JPEG q90 сверху,
WebP q80 снизу — мелкий текст на щитах, провода, листва и границы предметов
различий не показали.

### Что сделано в коде

- `app/preview/formats.py` — формат, расширение, MIME, качество по формату,
  список путей-кандидатов (текущий формат → прежний JPEG);
- `SCENE_PREVIEW_FORMAT` (`webp` по умолчанию, `jpeg` — прежнее поведение);
  `SCENE_PREVIEW_QUALITY` теперь необязателен: без него webp 80, jpeg 90;
- путь превью следует формату (`<photo_id>.webp`), поэтому при смене формата
  генератор видит фото как «без файла» и пересоздаёт его;
- API отдаёт превью с MIME по расширению и подставляет прежний JPEG, пока
  фото не пересоздано (404 в переходный период не появляется);
- QWEN (`analysis_input`) так же предпочитает текущий формат, затем прежний;
- валидатор принимает JPEG и WebP, остальные форматы по-прежнему отклоняет;
- `scripts/rebuild_previews.py --purge-legacy` удаляет прежние JPEG, но только
  те, рядом с которыми уже лежит файл текущего формата.

### Фактический результат на корпусе 583 фото

| | Было (JPEG q90) | Стало (WebP q80) | Δ |
|---|---:|---:|---:|
| SMALL, средний | 23,2 КБ | 13,3 КБ | −43 % |
| MIDDLE, средний | 291,5 КБ | 156,3 КБ | −46 % |
| `data/preview` всего | 179 МБ | 97 МБ | **−46 %** |

Очистка удалила 1166 прежних файлов (179,2 МБ); все 583 записи
`photo_previews` переведены на `.webp`, очередь PREVIEW пуста.

Прогноз на 57 000 фото: **≈9,5 ГБ вместо 18 ГБ**.

### Как вернуться к JPEG

`SCENE_PREVIEW_FORMAT=jpeg` в окружении, перезапуск API и preview-воркера,
затем `scripts/rebuild_previews.py` (пересоздаст в JPEG) и
`--purge-legacy` для уборки WebP. Миграций нет: формат не хранится в схеме,
путь и MIME выводятся из настройки.
