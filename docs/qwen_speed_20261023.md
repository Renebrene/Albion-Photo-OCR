# Как ускорить локальный QWEN: замеры и варианты (2026-10-23)

Модель: `qwen3-vl:4b-instruct` (Ollama, RTX 3060 12 ГБ). Все цифры ниже —
замеры на кропах текущего корпуса, без записи в базу.

## Куда уходит время одного ответа

| Часть | Время | Комментарий |
|---|---:|---|
| Всего | ~2,4 с | среднее по 1716 ответам |
| загрузка модели | 9 мс | модель уже прогрета |
| обработка входа | 814 мс | ~1255 токенов (в основном изображение) |
| генерация ответа | **1406 мс** | ~122 токена, ~11,5 мс/токен |
| прочее | ~165 мс | очередь, токенизация |

При повторных запросах текстовая часть промпта кэшируется, и `prompt_eval`
падает до ~14 мс — но изображение всё равно кодируется, поэтому на тёплом
стенде полный ответ был ~1,9 с. Главный рычаг — **генерация**.

## Что проверили

| Вариант | Время на фото | Эффект |
|---|---:|---|
| Один поток, после прогрева | 1,45 с | база |
| 2 потока параллельно | 1,45 с | **0 %** (латентность 2,60 с) |
| 3 потока параллельно | 1,42 с | **0 %** (латентность 3,41 с) |
| Картинка 1280 px вместо 2048 | 1,64–1,67 с | −12 %, поля совпали 15/16 |
| Картинка 1024 px | 1,64 с | −12 %, поля совпали 16/16 |

Разрешение влияет слабо: медиана кропа — 761 px, и только 3 % кропов
длиннее 1280 px. Для них уменьшение до 1280 даёт экономию времени без
потери полей (на малой выборке).

**Параллельные вызовы не ускоряют QWEN.** После прогрева шесть кропов
проходят за 8,7 с и в один поток, и в два, и в три: Ollama обслуживает
`qwen3vl` одним слотом, запросы сериализуются. Это же зафиксировано в
`docs/ollama_parallel_bench.md` (лог сервера: «model architecture does not
currently support parallel requests»). Второй и третий воркер только
увеличивают задержку каждого запроса.

Разница прогонов 43 и 69 минут объясняется не параллельностью, а объёмом:
в прошлый раз 583 фото уже имели описание, и этап поставил в очередь ~935;
в новый — все 1518. 935 × 2,65 с ≈ 41 мин, 1518 × 2,71 с ≈ 69 мин.

## Варианты по убыванию пользы

1. **Сократить ответ — проверено, выигрыш мал.** В контролируемом A/B
   (20 замеров на вариант, чередование промптов) лимит тегов 10 → 6 даёт
   −7 % (1,51 → 1,41 с), поля не меняются. Более короткий промпт
   (описание ≤ 15 слов, теги ≤ 5) даёт −18 %, но client совпал 2/4,
   brand 14/16, category 8/19 — не годится. Промежуточный вариант с
   примерами категорий оказался даже медленнее. Вывод: сокращение ответа
   не стоит потери категорий.
2. **Один кроп для большинства фото — механизм готов, выигрыш зависит от
   списка.** После прогона: 1396 фото с кропами, из них 1198 — один щит,
   198 — два; у 126 второй щит действительно другой, и они сосредоточены
   на 11 адресах. Второй кроп оставляется только для адресов из
   `SCENE_QWEN_MULTI_CROP_ADDRESSES` (пустой список — старое поведение,
   анализируются все кропы). Если включить все 11 адресов, второй кроп
   остаётся у 179 фото, экономия — **19 вызовов из 1716 (1,1 %)**. Если
   оставить только пять основных (193, 164, 211, 161, 158), экономия 46
   вызовов (2,7 %), но 6 фото на остальных адресах потеряют второй щит.

   **Включено с 2026-10-23:** `SCENE_QWEN_MULTI_CROP_ADDRESSES=192,193,211`
   (Малиновского 25 на Стачки, Малиновского 25 на Доватора, Зорге/Стачки).
   На текущем корпусе: 96 фото сохраняют два кропа, 102 переходят на один.
   Из 102 у 53 второй щит был другим — в основном Комарова 13 (40 фото);
   если он нужен, добавьте 164 (и при необходимости 158, 161).

   **Полный кадр вместо двух кропов** на этих адресах быстрее — 2,94 с
   против 5,54 с (1,88×), — но оба щита в структурированных полях он
   распознаёт только в 2 случаях из 8: в 4 находит один, в 2 — ни одного
   из эталонных брендов (выбирает доминирующий щит). Для адресов с двумя
   щитами два кропа остаются правильным выбором; экономия полного кадра
   не стоит потери второго рекламодателя.
3. **Модель 2B — проверена, не подходит.** `qwen3-vl:2b-instruct` скачана и
   прогнана на 20 кропах против 4B. Тёплый ответ ~1,5 с против ~2,4 с
   (до 1,6×), но качество рушится:

   | Поле | Совпало с 4B |
   |---|---:|
   | client | 1 / 4 (25 %) |
   | brand | 7 / 16 (44 %) |
   | category | **0 / 19 (0 %)** |
   | description, Jaccard | 0,23 |
   | tags, Jaccard | 0,23 |

   Пример: у щита МТС 4B даёт `brand=МТС, category=Телефонная связь`, а 2B —
   `brand=Лидер технологий, category=реклама`; у политического щита —
   `политическая реклама` против `выборы`. Экономия времени не оправдывает
   потерю полей; модель остаётся установленной только для экспериментов.
4. **Разрешение 1280 для крупных кропов.** Касается только 3 % файлов,
   экономия небольшая; можно включить как безопасный побочный эффект.

## Что не помогло / не нужно

- **Несколько кропов в одном запросе** — качество падает: второй щит
  распознаётся в 59 % против 86 % при отдельных запросах.
- **Увеличивать `max_output_tokens`** — ответы не обрезаются (максимум
  176 токенов из 768).
- **`keep_alive`** — модель уже остаётся тёплой, загрузка 9 мс.
- **Второй и третий QWEN-воркер** — архитектура `qwen3vl` обслуживает один
  слот; пропускная способность не растёт, задержка каждого запроса
  увеличивается. Замер: 6 кропов — 8,7 с в один поток, 8,7 с в два,
  8,5 с в три.

## Рекомендация

Локальный QWEN практически у предела: сокращение ответа даёт 7–18 % ценой
потери категорий, политика кропов — 1–3 % в зависимости от списка
адресов. Модель 2B отклонена (category 0/19), воркеры не помогают
(`qwen3vl` — один слот). Реальные варианты: пропуск QWEN за период и
отдельный прогон (уже реализовано), облачный провайдер для пиков, либо
принять ~69 минут на 1518 фото.
