# Как ускорить локальный QWEN: замеры и варианты (2026-10-23)

Модель: `qwen3-vl:4b-instruct` (Ollama, RTX 3060 12 ГБ). Все цифры ниже —
замеры на кропах текущего корпуса, без записи в базу.

## Куда уходит время одного ответа

| Часть | Время | Комментарий |
|---|---:|---|
| Всего | ~2,4 с | среднее по 1716 ответам |
| загрузка модели | 9 мс | модель уже прогрета |
| обработка входа | 814 мс | ~1255 токенов (в основном изображение) |
| генерация ответа | **1406 мс** | ~122 токена, ~11,5 мс/токен |
| прочее | ~165 мс | очередь, токенизация |

При повторных запросах текстовая часть промпта кэшируется, и `prompt_eval`
падает до ~14 мс — но изображение всё равно кодируется, поэтому на тёплом
стенде полный ответ был ~1,9 с. Главный рычаг — **генерация**.

## Что проверили

| Вариант | Время на фото | Эффект |
|---|---:|---|
| Один поток, после прогрева | 1,45 с | база |
| 2 потока параллельно | 1,45 с | **0 %** (латентность 2,60 с) |
| 3 потока параллельно | 1,42 с | **0 %** (латентность 3,41 с) |
| Картинка 1280 px вместо 2048 | 1,64–1,67 с | −12 %, поля совпали 15/16 |
| Картинка 1024 px | 1,64 с | −12 %, поля совпали 16/16 |

Разрешение влияет слабо: медиана кропа — 761 px, и только 3 % кропов
длиннее 1280 px. Для них уменьшение до 1280 даёт экономию времени без
потери полей (на малой выборке).

**Параллельные вызовы не ускоряют QWEN.** После прогрева шесть кропов
проходят за 8,7 с и в один поток, и в два, и в три: Ollama обслуживает
`qwen3vl` одним слотом, запросы сериализуются. Это же зафиксировано в
`docs/ollama_parallel_bench.md` (лог сервера: «model architecture does not
currently support parallel requests»). Второй и третий воркер только
увеличивают задержку каждого запроса.

Разница прогонов 43 и 69 минут объясняется не параллельностью, а объёмом:
в прошлый раз 583 фото уже имели описание, и этап поставил в очередь ~935;
в новый — все 1518. 935 × 2,65 с ≈ 41 мин, 1518 × 2,71 с ≈ 69 мин.

## Варианты по убыванию пользы

1. **Сократить ответ.** Генерация — 1,4 с из 2,4; при 122 токенах это
   главный рычаг. Ограничение до 5 тегов и описания в 15 слов даст
   примерно −25–30 %; нужно проверить на 20–30 кропах, что поля не
   деградировали.
2. **Один кроп для большинства фото.** После прогона 1396 фото с кропами:
   1198 — один щит, 198 — два. У 126 из 198 второй щит действительно другой
   бренд/клиент, и они сосредоточены на 11 адресах (59 — Малиновского 25 на
   Доватора, 40 — Комарова 13, 13 — Зорге/Стачки, остальные по 1–4). Если
   анализировать второй кроп только для адресов из списка (или по разнице
   pHash), экономия ~12 % вызовов без потери информации.
3. **Модель 2B.** В Ollama сейчас нет VL-модели 2B; `qwen3-vl:2b-instruct`
   можно скачать (~1,9 ГБ) и сравнить поля с 4B на размеченной выборке.
   Ожидаемо ~1,5–2× по генерации, но качество требует проверки.
4. **Разрешение 1280 для крупных кропов.** Касается только 3 % файлов,
   экономия небольшая; можно включить как безопасный побочный эффект.

## Что не помогло / не нужно

- **Несколько кропов в одном запросе** — качество падает: второй щит
  распознаётся в 59 % против 86 % при отдельных запросах.
- **Увеличивать `max_output_tokens`** — ответы не обрезаются (максимум
  176 токенов из 768).
- **`keep_alive`** — модель уже остаётся тёплой, загрузка 9 мс.
- **Второй и третий QWEN-воркер** — архитектура `qwen3vl` обслуживает один
  слот; пропускная способность не растёт, задержка каждого запроса
  увеличивается. Замер: 6 кропов — 8,7 с в один поток, 8,7 с в два,
  8,5 с в три.

## Рекомендация

Сначала сократить ответ (5 тегов, короткое описание) — это даёт 25–30 %
без изменения железа; затем ограничить второй кроп адресами/разницей
хэшей (−12 % вызовов). Модель 2B — после проверки качества на размеченной
выборке. Добавлять воркеры к QWEN смысла нет.
