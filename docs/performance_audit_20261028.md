# Аудит скорости фронта и бэка — 28.10.2026

Запрос владельца: «тормозит переключение подборок, грид не отображает даже
экраны; сделай аудит фронта и бэка по скорости, замеры, используй Playwright,
дай советы по оптимизации загрузки списков».

Замеры сделаны на рабочей базе (`photobase_ingest_test`, 56 936 фото, 1567
адресов, 27 видео), стенд — отдельный экземпляр API на `127.0.0.1:8011` без
аутентификации (те же код, БД и сборка SPA, что у пользователя), браузер —
Google Chrome через Playwright. Ничего в БД не менялось.

## Коротко: три причины «не показывает экраны»

1. **Запрос грида по кнопке считался 107 с.** Фильтр по закладке собирался в
   SQL как отдельный блок на КАЖДЫЙ адрес: у «Экранов» 95 адресов → 190
   коррелированных подзапросов, 72 КБ текста, 191 параметр. Счётчик по корпусу
   выполнялся ~100 с, страница ~5 с. **Исправлено**: один блок на набор
   (`= ANY(%s)`) — страница 0,08 с, счётчик 5,5 с, запрос целиком 6,1 с
   (было 107 с).
2. **После пустой группы кнопки переставали работать.** `setGroup` выходил
   раньше времени, если список строк пуст: «пусто» трактовалось как «грид ещё
   не грузился». Попадание в пустую группу (а пустых у нас четыре из пяти)
   навсегда оставляло грид пустым: подсветка кнопки менялась, запроса не было.
   **Исправлено**: отдельный признак `loadedOnce`.
3. **Счётчик задерживал показ фотографий.** Размер выборки для подписи «За
   период N фото» считался в том же запросе, что и страница, и стоил 5,5-6,5 с.
   **Исправлено**: страница отдаётся с `count=0` (фотографии появляются за
   0,3-0,7 с), счётчик запрашивается отдельно и дозаполняет подпись.

Плюс найден и исправлен отдельный «пожиратель» трафика, не связанный с
кнопками: **`/v1/pipeline/current` отдавал 3,38 МБ** (в манифесте прогона —
56 932 имени файлов), а шапка опрашивает его **каждые 3 с** и берёт оттуда
только стадии. Теперь 2 КБ (`files_count` вместо списка имён).

## Что ещё стоит сделать (по убыванию отдачи)

1. **Материализовать действующий адрес фото** — главное по влиянию.
   Сейчас «распознанный адрес» вычисляется на каждом запросе: последний вердикт
   HYBRID → слепок → адрес, и только потом сравнение. Отсюда 2,8 с на пустую
   группу и 5,5 с на счётчик. Таблица-проекция `photo_address(photo_id PK,
   address_id)` (или колонка `photos.address_id`), заполняемая при записи
   вердикта и ручного переопределения + бэкфилл, превращает фильтр по группе и
   счётчик в индексный доступ. Ориентир по стоимости: `SELECT count(*) FROM
   photos` на этом корпусе — 0,01 с, то есть счётчик станет десятками
   миллисекунд. Это миграция + правки в путях записи (hybrid, overrides) +
   бэкфилл; риск средний, поэтому отдельной задачей.
2. **Кэш панелей** (`/v1/addresses`, `/v1/clients`, `/v1/stats`). Каждая из них
   считается секунды и запрашивается по 3 раза на одну смену фильтра: список
   адресов и клиентов зависит только от (период, режим даты, группа, подборки),
   а не от прокрутки. Короткий кэш (10-30 с) с ключом из этих параметров и
   сбросом при изменениях пайплайна убирает и повторные секунды, и дубли.
3. **Счётчик фото** — уже разведён со страницей; если материализовать адрес, он
   станет дешёвым совсем. Отдельная мера на случай, если этого не делать:
   кэшировать `total` по сигнатуре фильтра (сейчас 5,5 с на каждое нажатие).
4. **Клиентский список не сужается кнопками.** Правая панель показывает всех
   клиентов корпуса (2,3-4,4 с на 200 записей), тогда как грид и адреса — по
   закладке. Если привести к тому же правилу, список станет и короче, и
   быстрее. Ожидает решения владельца.
5. **Манифест прогона в БД.** Хранится как JSONB со списком всех имён (56 932
   строки, ~3,4 МБ на строку таблицы). Мы убрали его из ответа API, но чтение
   `pipeline_runs` из БД всё ещё тянет этот JSONB на каждый опрос шапки
   (0,26 с вместо ~0,02 с). Вариант: хранить имена отдельной таблицей/файлом,
   а в манифесте — только `photo_cutoff` и счётчики для возобновления.
6. **gzip для JSON-ответов.** Сжатия нет вовсе (проверено: `Accept-Encoding:
   gzip` игнорируется). Даст 5-10× на текстовых ответах. Осторожно: включать
   middleware на всё приложение нельзя — под него попадёт потоковая отдача
   видео (`/stream`, Range). Нужен middleware, который жмёт только
   `application/json` и не растягивает потоковые ответы.
7. **Первая страница грида — 100 фото** (80 КБ JSON + 100 превью). Плитки уже
   с `loading="lazy"`, поэтому грузятся ~32 картинки. Если понадобится быстрее
   на слабом канале — уменьшить страницу до 50 первых и догружать по прокрутке
   (механика уже есть).
