# Аудит скорости фронта и бэка — 28.10.2026

Запрос владельца: «тормозит переключение подборок, грид не отображает даже
экраны; сделай аудит фронта и бэка по скорости, замеры, используй Playwright,
дай советы по оптимизации загрузки списков».

Замеры сделаны на рабочей базе (`photobase_ingest_test`, 56 936 фото, 1567
адресов, 27 видео), стенд — отдельный экземпляр API на `127.0.0.1:8011` без
аутентификации (те же код, БД и сборка SPA, что у пользователя), браузер —
Google Chrome через Playwright. Ничего в БД не менялось.

## Коротко: три причины «не показывает экраны»

1. **Запрос грида по кнопке считался 107 с.** Фильтр по закладке собирался в
   SQL как отдельный блок на КАЖДЫЙ адрес: у «Экранов» 95 адресов → 190
   коррелированных подзапросов, 72 КБ текста, 191 параметр. Счётчик по корпусу
   выполнялся ~100 с, страница ~5 с. **Исправлено**: один блок на набор
   (`= ANY(%s)`) — страница 0,08 с, счётчик 5,5 с, запрос целиком 6,1 с
   (было 107 с).
2. **После пустой группы кнопки переставали работать.** `setGroup` выходил
   раньше времени, если список строк пуст: «пусто» трактовалось как «грид ещё
   не грузился». Попадание в пустую группу (а пустых у нас четыре из пяти)
   навсегда оставляло грид пустым: подсветка кнопки менялась, запроса не было.
   **Исправлено**: отдельный признак `loadedOnce`.
3. **Счётчик задерживал показ фотографий.** Размер выборки для подписи «За
   период N фото» считался в том же запросе, что и страница, и стоил 5,5-6,5 с.
   **Исправлено**: страница отдаётся с `count=0` (фотографии появляются за
   0,3-0,7 с), счётчик запрашивается отдельно и дозаполняет подпись.

Плюс найден и исправлен отдельный «пожиратель» трафика, не связанный с
кнопками: **`/v1/pipeline/current` отдавал 3,38 МБ** (в манифесте прогона —
56 932 имени файлов), а шапка опрашивает его **каждые 3 с** и берёт оттуда
только стадии. Теперь 2 КБ (`files_count` вместо списка имён).

## Сделано после аудита (пункты 2-3 списка)

**Короткий кэш дорогих ответов** (`app/api/cache.py`, срок — `SCENE_API_CACHE_TTL`,
по умолчанию 10 с, 0 отключает). Кэшируются панель адресов, первая страница
панели клиентов, подвал и счётчик фото — всё это считается по всему корпусу и
зависит только от параметров фильтра. Замеры на живой базе:

| Запрос | Первый раз | Повтор в пределах TTL |
| --- | --- | --- |
| Панель адресов, группа «Экраны» | 1,40 с | **0,009 с** |
| Панель клиентов (200 записей) | 1,47 с | **0,005 с** |
| Счётчик фото по группе | 4,93 с | **0,030 с** |
| Другая группа (свой ключ) | 1,19 с | — |

Честные границы: данные меняет пайплайн, поэтому кэш намеренно короткий —
счётчики могут отстать не больше чем на TTL. Страницы грида, превью и карточки
не кэшируются: там важна свежесть, и запрос и так быстрый.

**Манифест прогона больше не читается для статуса** (пункт 5). В
`pipeline_runs.manifest` лежит список ВСЕХ имён файлов прогона — на корпусе в
56 932 фото это 3,4 МБ JSONB, а шапка опрашивает статус каждые 3 с и берёт
оттуда только стадии. Появился `with_manifest=False`: статус, история, ответы
на паузу и возобновление читаются без этой колонки, супервизор (возобновление
прогона) — как раньше, с манифестом. Замер на живой базе: `/v1/pipeline/current`
0,26 с → **0,008 с**, ответ 1 948 байт.

**Сжатие текстовых и JSON-ответов** (пункт 6, `app/api/compression.py`,
выключатель `SCENE_API_GZIP=0`). Свой middleware, а не `GZipMiddleware` из
Starlette: тот жмёт всё подряд, включая потоковое видео с Range, а здесь
сжатие только для `application/json`, `application/javascript`, `text/*`,
`image/svg+xml` и `application/xml`, только при известной длине от 1 КБ до
4 МБ, и никогда для 204/206/304 и уже сжатых ответов. Потоки и файлы не белого
списка проходят мимо без буферизации.

| Ответ | Без сжатия | С gzip |
| --- | --- | --- |
| Панель адресов (группа «Область и трассы») | 66 135 байт | **4 493 байта** |
| Бандл SPA (`index-*.js`) | 342 352 байта | **119 939 байт** |

На локальной сети выигрыш незаметен, по интернету — в разы меньше байт на
первой загрузке.

## Решения владельца (28.10.2026, после аудита)

- **Материализацию действующего адреса не делаем** («оставить как сейчас»):
  фото показываются за 0,3-0,7 с, счётчик догоняет в фоне. Пункт снят.
- **Правило действующего адреса подтверждено**: адрес берётся по соответствию
  photo_id — фото → его превью (`photo_previews.photo_id`) → последняя запись
  HYBRID (`hybrid_results.photo_id`, `status='DONE'`) → её `hybrid_final_id` →
  `address_fingerprints` → `address_directory`. Ручное переопределение
  (`photo_address_overrides.photo_id`) сильнее. Всё соединяется по photo_id,
  ничего не подбирается по имени файла — код уже таков (`_PHOTO_BASE`,
  `_verdict_source_sql`, `_latest_verdict_lateral_sql`).
- **Поисковая база клиентов/брендов и подсказок не зависит от списка адресов**:
  панель клиентов больше не сужается выбранными адресами (ни в приоритете по
  адресам, ни при переключении кнопок верхней панели), строка поиска и подсказки
  (`/v1/search/suggestions`) ищут по всему корпусу. Пункт «клиентский список по
  закладке» из списка ниже снят — владелец хочет обратное.

## Тег адреса — по решению владельца

Тег показывает название адреса как список и **без буквы стороны**: в каталоге
она уже входит в название («Космонавтов 42 А на Северный», «Курчатова /
Хасанская Б», «339 Стрелковой Дивизии, 7/ Содружества ул., A1»), и дописывание
давало дубль вида «…, A2». Исправлено то, что было настоящей ошибкой: клик по
строке панели отмечает все поверхности стороны (`addr:<id>`), и на каждое
значение рисовался свой тег — лишние показывали «addr:157». Теперь на сторону
один тег, снятие снимает всю сторону.

## Что ещё стоит сделать (по убыванию отдачи)

1. ~~Материализовать действующий адрес фото~~ — **снято решением владельца**.
   Сейчас «распознанный адрес» вычисляется на каждом запросе: последний вердикт
   HYBRID → слепок → адрес, и только потом сравнение. Отсюда 2,8 с на пустую
   группу и 5,5 с на счётчик. Таблица-проекция `photo_address(photo_id PK,
   address_id)` (или колонка `photos.address_id`), заполняемая при записи
   вердикта и ручного переопределения + бэкфилл, превращает фильтр по группе и
   счётчик в индексный доступ. Ориентир по стоимости: `SELECT count(*) FROM
   photos` на этом корпусе — 0,01 с, то есть счётчик станет десятками
   миллисекунд. Это миграция + правки в путях записи (hybrid, overrides) +
   бэкфилл; риск средний, поэтому отдельной задачей.
2. **Кэш панелей** (`/v1/addresses`, `/v1/clients`, `/v1/stats`). Каждая из них
   считается секунды и запрашивается по 3 раза на одну смену фильтра: список
   адресов и клиентов зависит только от (период, режим даты, группа, подборки),
   а не от прокрутки. Короткий кэш (10-30 с) с ключом из этих параметров и
   сбросом при изменениях пайплайна убирает и повторные секунды, и дубли.
3. **Счётчик фото** — уже разведён со страницей; если материализовать адрес, он
   станет дешёвым совсем. Отдельная мера на случай, если этого не делать:
   кэшировать `total` по сигнатуре фильтра (сейчас 5,5 с на каждое нажатие).
4. ~~**Клиентский список не сужается кнопками.**~~ — **снято**: владелец
   подтвердил, что база поиска клиентов и брендов не должна зависеть от списка
   адресов (сделано, см. выше).
5. **Манифест прогона в БД.** Хранится как JSONB со списком всех имён (56 932
   строки, ~3,4 МБ на строку таблицы). Мы убрали его из ответа API, но чтение
   `pipeline_runs` из БД всё ещё тянет этот JSONB на каждый опрос шапки
   (0,26 с вместо ~0,02 с). Вариант: хранить имена отдельной таблицей/файлом,
   а в манифесте — только `photo_cutoff` и счётчики для возобновления.
6. **gzip для JSON-ответов.** Сжатия нет вовсе (проверено: `Accept-Encoding:
   gzip` игнорируется). Даст 5-10× на текстовых ответах. Осторожно: включать
   middleware на всё приложение нельзя — под него попадёт потоковая отдача
   видео (`/stream`, Range). Нужен middleware, который жмёт только
   `application/json` и не растягивает потоковые ответы.
7. ~~**Первая страница грида — 100 фото**~~ — **сделано (28.10.2026)**:
   размер страницы 100 → 50 (`PAGE_SIZE` в `stores/photos.js`). Первая отрисовка
   получает 50 карточек вместо 100: ответ 40 568 байт вместо 80 536, превью —
   примерно вдвое меньше (плитки ленивые), разметка вдвое короче. Прокрутка
   догружает те же страницы тем же курсором; поведение «догружаем, пока экран
   не заполнен» сохранено.
