CLIP VISUAL SEARCH
==================

1. НАЗНАЧЕНИЕ

Визуальный поиск похожих объявлений по кропам щитов. openai/clip-vit-base-patch32
(ViT-B/32, 151M параметров, 512-d) кодирует каждый billboard-кроп; поиск —
косинусная близость (FAISS IndexFlatIP по L2-нормализованным векторам).
Находит ту же кампанию в другом ракурсе/освещении, где не совпадают ни
метаданные QWEN, ни перцептуальные хеши (app/api/crop_search.py).

Это НЕ распознавание адресов и НЕ часть DINO/HYBRID: CLIP-индекс живёт
отдельно, только для поиска. Дино-слепки и вердикты не затрагиваются.

Архитектурная цепочка:

  photo_regions (kind='billboard', crop_path)
      |
  CLIP EMBED (CPU, 224x224)
      |
  data/clip/ : clip_index.faiss + clip_meta.jsonl + clip_embeddings.npy
      |
  GET /v1/search/visual (region_id | photo_id)   POST /v1/search/visual (файл)
      |
  грид: «Похожие» / поиск по медиа: источник «Визуально»

2. ФАЙЛЫ

data/clip/ (SCENE_CLIP_ROOT, по умолчанию <SCENE_DATA>/clip):

  clip_index.faiss      IndexFlatIP, 512-d, точный поиск; ~78 МБ на 39k
  clip_meta.jsonl       строка на вектор: region_id, photo_id, crop_path,
                        score (детекции); строка i == вектор i индекса
  clip_embeddings.npy   сырые векторы (f32, L2-нормализованы) — для инкремента
  index_info.json       модель, built_at, vectors, mode

При загрузке сервис проверяет согласованность (ntotal == число мета-строк);
рассогласование (например, сбой между os.replace) требует пересборки —
данные при этом не теряются, поиск просто отключён (503).

3. СКОРОСТЬ И РЕСУРСЫ (замеры 2026-11-17/18, CPU 12 ядер, делит CPU с QWEN)

  Эмбеддинг кропа:  34 мс свободный CPU, 55 мс при бэклоге QWEN
  Полный ребилд:    39 236 кропов ~ 22-36 мин (зависит от загрузки)
  Поиск по индексу: точный перебор, ~1 мс на 39k; запрос по сохранённому
                    region_id не требует модели (~20 мс суммарно)
  Запрос по файлу:  CLIP-кодирование ~35 мс (первый вызов: загрузка модели
                    2-5 с; модель держится в процессе API)
  RAM:              модель ~600 МБ + индекс 78 МБ (в процессе API)

GPU не используется: скрипт требует CUDA_VISIBLE_DEVICES=""; GPU остаётся
за QWEN/DINO. Все операции в API — ленивые, при старте сервиса ничего
не грузится.

4. API (scope read; searches_router)

  GET  /v1/search/visual/status
       {available, vectors, dim, model, built_at, db_regions, stale, pending}
       stale=True — в БД больше регионов, чем в индексе (ждёт ребилда);
       pending — векторы, поглощённые в память, но ещё не сброшенные на диск.

  GET  /v1/search/visual?region_id=123&top_k=24
  GET  /v1/search/visual?photo_id=PH_xxx&top_k=24&days=30
       Ровно один из region_id / photo_id (для фото — его первый кроп).
       days — окно по дате съёмки (photos.taken_at): 0 = всё время, иначе
       выдача режется диапазоном «сегодня − days». Совпадения с фото запроса
       исключаются. Ответ: matches[{region_id, photo_id, crop_path, score,
       crop_index, address_id, address, brand, client, taken_at,
       created_at}], count. Ошибки: 404 (нет региона/фото в индексе), 503
       (индекс не собран/рассогласован), 422 (параметры).

  POST /v1/search/visual  (multipart: file, top_k)
       Файл декодируется в памяти PIL-декодером, лимит 10 МБ, на диск не
       пишется, заданий не создаёт — синхронный ответ.

  GET/POST /v1/favorites, DELETE /v1/favorites/{photo_id}
       Избранные фото пользователя — служебная фото-подборка «Избранные
       фото» (scope='photos', schema/009). Отдельной таблицы и миграции
       нет; лимит 5000 фото. Гость: GET доступен, запись требует
       collections:write (у гостя его нет — 403).

Фронтенд: PhotosGrid — «Похожие» в меню карточки и в шапке просмотрщика:
сетка ровно в 3 колонки с чекбоксами, на карточке даты съёмки и загрузки,
переключатель диапазона в шапке (неделя → месяц → 3 месяца → полгода → год →
всё время). Score видит только администратор; у менеджера/гостя его нет.
Кнопки «Очистить», «Перейти в избранное» (отмеченные фото → избранное и
сразу фильтр грида по нему), «Закрыть» (снимает отметки). В умном поиске
по медиа — кнопка «Визуально: N» (источники QWEN + dHash + CLIP, OR).

5. ОБНОВЛЕНИЕ

Реальное время (с 18.11.2026): вектор нового кропа считается прямо в
воркере детекции (app/billboard/pipeline.py → _clip_queue_new_crops,
CPU ~35-55 мс) и дописывается в data/clip/pending.jsonl под fcntl-lock.
Сервис при каждом поиске/статусе поглощает очередь: векторы мгновенно
появляются в поиске (в памяти), на диск сбрасываются порогом — 100 векторов
или 10 минут (index + meta + npy атомарно). Идемпотентно по region_id;
pending очищается только после успешной публикации — падение процесса
ничего не теряет. Ошибка CLIP не валит детекцию (логируется и пропускается).

Ночной fallback:
  scripts/clip_rebuild.py            # инкремент: только новые region_id
  scripts/clip_rebuild.py --full     # полный пересбор (чистит пропавшие)
  scripts/clip_rebuild.py --json     # строка JSON для мониторинга

Запись атомарная (tmp → os.replace); инкремент хвосты не удаляет — пропавшие
кропы остаются в индексе до полного ребилда. Ночной шаг добавлен в
scene-maintenance.service (после cleanup-шагов), CUDA_VISIBLE_DEVICES="".
Память: модель CLIP (~600 МБ) лениво загружается в каждом воркер-процессе,
создающем кропы (scene-billboard-worker, scene-qwen-worker через
ensure_crops) и в API для поиска по файлу.

6. ОГРАНИЧЕНИЯ

- ViT-B/32 — компромисс по качеству/скорости; мелкий текст (телефоны)
  CLIP не читает. При необходимости B/16 даёт лучше, но ~4x дольше CPU.
- Текстовый поиск (text encoder) в фазу 1 НЕ включён: RU-запросы у B/32
  грубые; кандидат на фазу 2 — многоязычный энкодер (rusclip/jina-clip).
- Поиск по фото без billboard-кропов невозможен (индекс только по кропам) —
  404 с пояснением. Полно-кадровый индекс — отдельная фаза.
- На >500k векторов стоит перейти на IVF/HNSW и/или pgvector; сейчас
  IndexFlatIP дешевле и без миграций.
