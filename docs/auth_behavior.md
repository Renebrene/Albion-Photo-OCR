# Алгоритм авторизации и сохранения настроек

Дата: 2026-10-17

## 1. Принципы

1. **Сервер — единственный источник правды.** Каждая ручка проверяет scope;
   UI только прячет недоступное, но не заменяет проверку.
2. **Fail-closed.** Нет учётных данных → 401; нет нужного scope → 403;
   неизвестная роль → права `read` (как у Гостя).
3. Настройки интерфейса принадлежат **пользователю**, а не браузеру; у Гостя
   они не сохраняются вовсе.

## 2. Роли и scopes (`app/api/auth.py::ROLE_SCOPES`)

| Роль | Scopes |
|---|---|
| Администратор | `*` |
| Менеджер | `read`, `collections:write`, `searches:write`, `upload:write`, `photos:write`, `jobs:read`, `jobs:write`, `addresses:write`, `videos:read`, `videos:write`, `videos:download`, `originals` |
| Гость | `read` |

`users:manage` и `settings:write` — только Администратор.

## 3. Алгоритм входа и отрисовки

```
SPA старт
  → session.load(): GET /v1/auth/me                          (публичная)
  → user = {user_id, name, role}, auth_enabled
  → если auth_enabled и user = null → экран входа
  → иначе afterAuth():
       canPersist = !auth_enabled || role !== 'Гость'
       display.setPersistence(canPersist)
       если !canPersist: display.reset()                    (заводские настройки)
       photos.loadSelectionState({persist: canPersist})
       если canPersist: display.loadFromServer()            (GET /v1/selection)
       booted = true → рендер интерфейса
```

Маршрутизатор (`frontend/src/router/index.js`):

```
переход на /technical
  → роль ∈ {Администратор, Менеджер} ? маршрут : redirect '/'
```

Серверных ручек технического раздела нет в публичном API: пользователи
(`users:manage`), настройки QWEN (`settings:write`) закрыты scope-проверкой.

## 3.1. Кука сессии: только для чтения

`POST /v1/auth/login` и `GET /v1/auth/me` выставляют `HttpOnly`-куку
`scene_session` (`SameSite=Lax`, `Path=/`, срок — `SCENE_COOKIE_MAX_AGE`,
по умолчанию 7 дней). `POST /v1/auth/logout` её удаляет.

Зачем: `<img>`/`<link>` не умеют `Authorization`, поэтому превью и
оригиналы загружаются только через `fetch` + blob. Кука позволяет браузеру
грузить превью нативно (`loading="lazy"`, кэш HTTP, параллельные запросы) —
это заметно быстрее при прокрутке грида.

Правила (закреплены `tests/test_role_scopes.py`):

| Запрос | Заголовок | Кука | Результат |
|---|---|---|---|
| `GET`/`HEAD` | `Bearer …` | — | по токену |
| `GET`/`HEAD` | — | есть | по куке |
| `GET`/`HEAD` | `Bearer …` | есть | **заголовок важнее**; неверный заголовок не подменяется кукой (401) |
| `POST`/`PUT`/`PATCH`/`DELETE` | — | есть | **401** — изменяющие запросы требуют `Authorization` |

Ограничение куки чтением — защита от CSRF: браузер прикладывает куку сам, а
`SameSite=Lax` дополнительно не отправляет её с чужих сайтов на
изменяющие запросы. Поэтому UI продолжает слать `Authorization` на все
записи, а сервер на них куку не смотрит.

`SCENE_COOKIE_SECURE=1` включает флаг `Secure` — обязателен, если сервер
доступен по HTTPS (иначе браузер не сохранит куку). Пока сайт работает по
plain HTTP внутри доверенной сети, значение остаётся `0`.

## 4. Гость: что видно и что запрещено

| Возможность | UI | Сервер |
|---|---|---|
| Адреса, грид, клиенты | видит | `read` |
| Фильтры, текстовая строка поиска | доступны | `read` |
| Переключение Фотогалерея/Видео | доступно | `read` |
| Поиск по загруженному фото/видео | **скрыт** (камера, «Авто», окно ручного поиска) | `searches:write` → 403 |
| Технический раздел | шестерёнка скрыта, `/technical` редиректит | админ-ручки за scope |
| Скачивание фото/видео/архива, «Оригинал», «Сохранить» | **скрыты** (кнопки, контекстное меню, карточка) | `originals`, `videos:download` → 403 |
| Окно редактирования карточки (адрес, текст, пересканирование) | **скрыто** | `addresses:write`, `photos:write`, `jobs:write` → 403 |
| Подборки (создание/сохранение, «В подборку») | **скрыты** | `collections:write` → 403 |
| Сохранение настроек | отключено | `PUT /v1/selection` → 403 |

Ключевые точки UI:

- `PhotosGrid.vue`: `canUseCollective` (Администратор/Менеджер) гейтит
  скачивание, подборки, «Оригинал/Сохранить», редактирование адреса;
  `canSearchMedia` — камеру и ручной поиск; `canRunQwen` — пересканирование.
- `VideosGrid.vue`: `isStaff` гейтит воспроизведение, сжатие и скачивание.
- `App.vue`: `canUseTech` гейтит шестерёнку; `afterAuth()` управляет
  сохранением.
- `router/index.js`: guard `/technical`.

## 5. Алгоритм сохранения настроек

| Состояние | Кто | Куда |
|---|---|---|
| Раскладка, панели, поля списка, режим имён скачивания | staff | `localStorage` + `PUT /v1/selection {display}` (debounce 800 мс) |
| Базовая раскладка («Вернуть базовые», файл) | staff | `localStorage` + `PUT /v1/selection {display_base}` |
| Отметки фото/адресов/клиентов | — | **не сохраняются между сессиями** (владелец, 2026-10-17): при входе грид показывает все фото, выделения адресов/клиентов пусты |
| Гость | — | **ничего не сохраняется**: ни localStorage, ни сервер; при каждом входе заводские значения |

Сервер хранит состояние в `manager_selections.state` (schema/015); ключ
`selected`/`display`/`display_base` сливается, а не перезаписывается целиком.

## Блокировка подбора пароля и частота запросов (2026-10-23)

Счётчики в `app/api/security.py` не только показываются в «Системе», но и
действуют.

### Блокировка входа

`SCENE_LOGIN_FAILURE_LIMIT` неудачных попыток входа с одного адреса за
`SCENE_LOGIN_FAILURE_WINDOW` секунд (по умолчанию 10 за 10 минут) блокируют
вход с этого адреса: `POST /api/v1/auth/login` отвечает **429** с заголовком
`Retry-After` (секунды до конца окна). Удачный вход обнуляет счётчик ошибок
этого адреса — человек, который в итоге ввёл верный пароль, не остаётся
заблокированным.

- Правило применяется **до** обращения к таблице пользователей, поэтому 429
  приходит и при недоступной БД, и не зависит от того, существует ли логин.
- Это не замена сложности пароля и не защита от распределённого перебора:
  считается адрес, а не логин. Для интернета нужен ещё внешний лимит (прокси).
- Выключить: `SCENE_LOGIN_LOCKOUT=0`.

### Ограничение частоты запросов

`SCENE_API_RATE_LIMIT` — число запросов в минуту на адрес, **по умолчанию 0
(выключено)**. Это осознанно: одна страница грида законно запрашивает сотни
превью, поэтому включённый лимит с малым значением ломает интерфейс. Включать
стоит при публикации API в интернет, значением заведомо выше реального
профиля (например, 1200).

При превышении — **429** с `Retry-After`. `/api/health` не ограничивается
никогда: по нему проверяют живость сервиса.

### Документация API закрыта

`/docs`, `/redoc` и `/openapi.json` по умолчанию возвращают **404**
(`SCENE_ENABLE_DOCS=1` открывает их для локальной разработки). Схема
перечисляет все маршруты, а сервис доступен из локальной сети и через
тоннель. Когда документация выключена, эти адреса не подменяются оболочкой
SPA — иначе `/docs` отдавал бы HTML приложения со статусом 200 и выглядел бы
как открытая документация.

Проверка вручную:

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8010/docs          # 404
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8010/openapi.json  # 404
```

Тесты: `tests/test_login_guard.py`.

## Хранение сессионных токенов (2026-10-23)

Bearer-токен и есть идентификатор сессии, поэтому раньше в `public.sessions`
лежал он сам: дамп базы (бэкап, реплика, лог тяжёлого запроса) отдавал рабочие
учётные данные всех вошедших пользователей.

Миграция `schema/045_session_token_hash.sql` это меняет:

- колонка `session_id` **удалена**, вместо неё `token_hash` — SHA-256 от токена,
  он же первичный ключ (`ux_sessions_token_hash`);
- хэш считается функцией ядра `sha256()` (pgcrypto не нужен);
- существующие сессии **сохраняются**: хэш вычислен из лежавшего в базе
  значения, пока колонка была на месте. Проверено на рабочей базе: сессия,
  созданная до миграции, после неё продолжает находиться (75 сессий), а вход и
  выход через API работают как раньше;
- **API нужно перезапускать сразу после миграции**: работающий процесс ещё
  ищет сессию по удалённой колонке. Порядок: `systemctl --user stop scene-api`
  → `python scripts/migrate.py` → `systemctl --user start scene-api`.

Поиск по хэшу — одно сравнение по индексу, поэтому скорость не меняется.
`hash_session_token()` в `app/users/database.py` — единственное место, где это
превращение делается; пароль пользователя хэшируется отдельно
(`app/users/security.py`).

Откат невозможен без потери сессий: восстановить открытые токены нельзя (в этом
и смысл). SQL отката — в шапке миграции; после него всем нужно войти заново.

Тесты: `tests/test_session_tokens.py`. Проверки с базой выполняются только при
явном `SCENE_TEST_DB=1` (см. `docs/testing.md`); без него проверяются хэш и
отсутствие колонки с открытым токеном в коде.
