# Фронтенд: старый NiceGUI → целевой Quasar

**Статус:** описание исторического фронтенда (по `111/`), план переноса и **журнал реализации**. Перенос на Vue 3 + Quasar **выполнен** (`frontend/`, раздел 6, «Срезы»); разделы 1–5 сохраняют исторический контекст. Контракт API — [`api_target.yaml`](api_target.yaml), ТЗ — [`future_implementation_tz.md`](future_implementation_tz.md).

## 1. Что есть сейчас в репозитории

Текущий UI — минимальный NiceGUI в `app/main.py`: одна страница с тремя вкладками (`Создать слепок`, `Распознавание`, `База слепков`), синхронные вызовы `SceneEmbedder`/`FingerprintManager`/`SceneRecognizer`, создание моделей при импорте модуля. Это демонстрационный UI для fingerprint-слепков, а не фото-грид.

## 2. Исторический фронтенд (легаси NiceGUI, `app/web/`)

Более развитый фронтенд существовал в легаси-проекте `scene_fingerprint_mvp_v02` под `app/web/`. Заголовок окна — «АЛЬБИОН: Фотобаза. Офис».

Модульная структура:

- `app/web/main.py` — сборка страницы.
- `app/web/state.py`, `session.py` — состояние/сессия (в т.ч. `STATE.refresh_photos`).
- `app/web/config.py` — пути/конфиг.
- `app/web/frontend_v01.py`, `frontend_v02.py` — ранние версии.
- `app/web/components/`:
  - `header.py`, `filters.py`,
  - `photos.py` — грид фотографий (самый крупный модуль),
  - `addresses.py`, `clients.py` — панели-списки,
  - `collections.py` — подборки,
  - `search.py` — поиск (в легаси — только по данным Qwen, без DINO),
  - `technical.py`.
- `app/web/components/technical_modules/`: `photo_processing.py`, `qwen.py`, `automation.py`, `users.py`, `data.py`.
- `app/web/*_db.py`: `photo_db.py`, `client_db.py`, `directory_db.py`, `users_db.py` — доступ к PostgreSQL через `psycopg2` с `PG_CONFIG = {host: localhost, port: 5432, dbname: "photobase", user: "lora"}` (легаси-схема).

Типовая раскладка (из `111/chat_chunks/chunk_178.md`, `app/web/main.py`):


Левая фиксированная колонка (~580px): карточка «Период» (`ui.radio` «Дата съёмки/Дата загрузки», `ui.select` «Текущий месяц/Предыдущий месяц/Все даты/Выбрать период»), ниже — две равные прокручиваемые панели «Адреса» и «Клиенты». Правая часть — грид фотографий (`build_photos()`), обновляемый через колбэк `STATE.refresh_photos`.

Виджеты NiceGUI, которые использовались: `ui.page`, `ui.row/column/card/label`, `ui.tabs/ui.tab_panel`, `ui.radio`, `ui.select`, `ui.input`, `ui.scroll_area`, `ui.dialog`, всплывающие окна («Показать фотографии»). Стилизация — Tailwind-классы через `.classes(...)` + `.style(...)`.

Легаси-грид грузил превью, показывал адрес/клиента/статус Qwen, поиск и подборки; оригиналы — по клику. Технический раздел (обработка, qwen, automaton, users, data) — отдельные модули.

## 3. Целевой фронтенд: Vue 3 + Quasar

Полностью отдельный SPA, работающий с FastAPI по [`api_target.yaml`](api_target.yaml). Никакого прямого доступа к PostgreSQL из фронтенда.

Принципы:

- данные только через REST API; оригиналы и previews — через API с проверкой прав;
- грид показывает **preview**, оригинал не грузится по умолчанию;
- серверная **cursor pagination** (≤100 элементов), ленивая подгрузка (`q-infinite-scroll`);
- UI не сортирует/не копирует исходники и не пересчитывает распознавание;
- статусы обработки — из API (реальные job/batch), а не отдельный журнал.

### 3.1 Соответствие виджетов NiceGUI → Quasar

| NiceGUI | Quasar |
|---|---|
| `ui.tabs` / `ui.tab_panel` | `q-tabs` / `q-tab-panels` / `q-route-tab` (Vue Router) |
| `ui.card` | `q-card` / `q-card-section` |
| `ui.row` / `ui.column` | `q-...` + flex-классы |
| `ui.select` | `q-select` |
| `ui.radio` | `q-option-group` / `q-radio` |
| `ui.input` | `q-input` |
| `ui.scroll_area` | `q-scroll-area` / `q-infinite-scroll` |
| `ui.dialog` | `q-dialog` |
| грид фото | `q-card` в `q-page` + `q-infinite-scroll`, либо `q-table` в grid-режиме |
| состояние (`STATE`) | Pinia store |
| HTTP | `axios`/`fetch` к FastAPI |

### 3.2 Экраны (v1)

1. **Фото (GRID)** — фильтры (адрес, клиент, дата, подборка, поиск), кнопка «Показать фотографии», сетка карточек на SMALL-preview, lazy-load, клик → просмотр (MIDDLE, далее original при наличии прав), отображение результата распознавания и score.
2. **Обработка (технический раздел)** — запуск/статус INGEST, DINO batch (NORMAL/FORCE_RERUN), HYBRID, прогресс и per-item ошибки; подтверждение дорогих операций; отображение реального состояния из API.
3. **Подборки/поиск** — saved searches (условия, не копия выдачи), collections (набор `photo_id`); мультизапрос AND/OR — следующий этап.
4. **Администрирование** — пользователи/роли (по правам), аудит.

### 3.3 Данные и безопасность

- авторизация OIDC/OAuth2, scopes (`photos:read`, `ingest:write`, `jobs:read`, `jobs:write`, `admin`);
- previews/оригиналы — только через авторизованный endpoint; фронтенд не принимает произвольные пути;
- CORS — allowlist UI origin; no secrets/EXIF в UI без необходимости.

### 3.4 Технологический стек

`Vue 3` + `Vue Router` + `Pinia` + `Quasar` (+ Vite). Сборка отдельным артефактом; раздача статики — reverse proxy или FastAPI static.

## 4. Что переиспользовать из легаси-фронтенда

- **Раскладку** «Период + Адреса/Клиенты + GRID» — как основу экрана «Фото».
- **Модульность** (header/filters/photos/addresses/clients/collections/search/technical) — перенести как Vue-компоненты.
- **Семантику фильтров** (период: дата съёмки/загрузки; месяцы; адрес/клиент/подборка; поиск) — в фильтры грида.
- **Смысл технических модулей** (обработка, qwen, automation, users, data) — как отдельные разделы SPA.

Не переиспользовать: прямой `psycopg2` из UI, легаси-схему `photos` (`address/client/qwen_*`), Qwen-специфичный поиск как единственный источник.

## 5. Что нужно решить до реализации

- Нормализованные сущности адресов/клиентов (или фильтры по строкам) — влияет на фильтры и API.
- Источник адреса/клиента: HYBRID-вердикт (fingerprint-id) vs Qwen-метаданные vs отдельный реестр (см. [`qwen_process.md`](qwen_process.md)).
- Единый контракт DTO (Pydantic) для грида/поиска/статусов.
- Аутентификация и права на просмотр previews/originals.

## 6. Реализованный срез 1 (2026-10-13)

Первый вертикальный срез: read-only API + Quasar GRID на реальной БД. Аутентификации **нет** — только локальная разработка.

### Backend — `app/api/` (FastAPI)

- `GET /api/health` → `{"status":"ok","version":...}`
- `GET /api/v1/photos?limit=&cursor=&q=` → страница зарегистрированных фото (cursor-пагинация по `photo_id`, `limit` 1..100, `q` — подстрока в `filename`); ответ `{items, next_cursor}`.
- `GET /api/v1/photos/{photo_id}` → сводка фото.
- `GET /api/v1/photos/{photo_id}/previews/{small|middle}` → JPEG-превью.

Особенности: `photo_id` валидируется по `^PH_[0-9a-f]{24}$` (иначе 404); путь превью строится из `photo_id` и `SCENE_PREVIEW_ROOT`, а не из пользовательского ввода; подключение к БД — через `INGEST_DB_*`. Конфиг API не тянет torch (`app/api/config.py`). CORS — по `SCENE_CORS_ORIGINS` (по умолчанию localhost:5173).

Тесты: `tests/test_api.py` (health, валидация, 404; list/cursor — с БД).

### Срез 2 — статусы обработки (read-only)

- `GET /api/v1/batches/dino?limit=&cursor=` — список DINO batch-ей (тип, статус, счётчики, тайминги).
- `GET /api/v1/batches/dino/{batch_id}` — детали batch (`404`, если нет).
- `GET /api/v1/batches/dino/{batch_id}/runs?limit=&cursor=` — runs batch-а.
- `GET /api/v1/hybrid/runs?limit=&cursor=` — список HYBRID-запусков.
- Экран «Обработка» в SPA: вкладки DINO batches / HYBRID runs, статус-бейджи, клик по batch → диалог со списком runs.

Запуск обработки (INGEST/DINO/HYBRID) в этом срезе **не реализован** — отдельный этап (enqueue + фоновый worker, без inference в request handler).

### Срез 3 — auth + originals

- `app/api/auth.py`: **опциональные** bearer-токены через `SCENE_API_TOKENS`
  (формат `token:scope1|scope2`, повторяющиеся через запятую, `*` = все scope).
  Если переменная не задана — API открыт (локальная разработка).
- Read-эндпоинты требуют scope `read`; `GET /api/v1/photos/{photo_id}/original`
  требует scope `originals` и отдаёт зарегистрированный исходник (путь берётся
  из БД, не из клиента). `GET /api/health` всегда открыт.
- SPA в этом срезе работает без токенов (если включить `SCENE_API_TOKENS`,
  фронтенду понадобится поле токена — следующий этап).
- OIDC/OAuth2 — будущая замена этого слоя без изменения эндпоинтов.

### Срез 4 — запуск обработки (очередь + worker)

- Очередь: таблица `job_queue` (`schema/006_job_queue.sql`). API только ставит задание, inference выполняет отдельный процесс.
- `POST /api/v1/jobs/dino-batch` (scope `jobs:write`) — создаёт DINO batch (`NORMAL`/`FORCE_RERUN`) и ставит задание → `202 {job_id, batch_id}`.
- `POST /api/v1/jobs/hybrid` (scope `jobs:write`) — создаёт HYBRID run для `DONE` batch и ставит задание → `202 {job_id, hybrid_run_id}`; неготовый batch → `409`.
- `GET /api/v1/jobs` и `GET /api/v1/jobs/{job_id}` (scope `jobs:read`) — статусы.
- **Worker:** `python -m app.jobs.worker` (один проход) или `--watch`. Забирает задание атомарно (`FOR UPDATE SKIP LOCKED`) и вызывает `app.dino.runner.run_batch` / `app.hybrid.runner.run`. Inference **никогда** не идёт в HTTP-хендлере.
- UI: кнопка «Запустить DINO (NORMAL)», действие «HYBRID» у `DONE`-batch и вкладка «Задания».
- Тесты: `tests/test_jobs_queue.py`, `tests/test_api_jobs.py`.

### Срез 5 — QWEN (текстовые метаданные)

- Параллельный процесс, независимый от DINO/HYBRID: `app/qwen/` + очередь (`job_type = QWEN_PHOTO`). Схема: `schema/007_qwen.sql` (таблица `photo_qwen`).
- Модель — через локальный **Ollama**; имя конфигурируемо (`QWEN_MODEL`, по умолчанию `qwen3-vl:8b`), `OLLAMA_URL`. Изображение (MPO → frame 0) ужимается и отправляется в `/api/chat` с `format=json`, `think=false`.
- Извлекаются поля: `description`, `address`, `client`, `brand`, `category`, `tags`.
- `POST /api/v1/jobs/qwen` (scope `jobs:write`) — ставит задания на указанные `photo_ids` или на все фото; выполняет тот же `app.jobs.worker`.
- `GET /api/v1/photos` расширен полями `address`/`client` и фильтрами `address`/`client`.
  **Источник адреса — распознавание** (последний `hybrid_results.hybrid_final_id`, fallback `dino_runs.dino_best_id`), **клиент — из QWEN** (`photo_qwen.client`).
- UI: в карточках GRID — адрес/клиент и описание; фильтры «Адрес (QWEN)»/«Клиент (QWEN)»; на экране «Обработка» — кнопка «Запустить QWEN».
- Тесты: `tests/test_qwen.py` (парсинг — всегда; БД — с базой; живой прогон — `QWEN_LIVE_TEST=1`).

### Срез 6 — выбор модели QWEN и авто-выгрузка

- Модель выбирается в рантайме и хранится в `app_settings` (`schema/008_settings.sql`, ключ `qwen_model`); при отсутствии значения используется env `QWEN_MODEL`. `app/settings_store.py`.
- `GET /api/v1/qwen/models` — список моделей Ollama + текущая; `PUT /api/v1/qwen/model` (scope `jobs:write`) — выбрать; `POST /api/v1/qwen/unload` (scope `jobs:write`) — выгрузить из памяти.
- **Авто-выгрузка:** каждый запрос к Ollama идёт с `keep_alive: 0`, поэтому модель выгружается сразу после обработки фото (проверено: после прогона `ollama ps` пуст).
- UI: экран «Настройки» — выбор модели из списка, кнопки «Сохранить»/«Выгрузить из памяти».
- Рекомендация для 12 ГБ VRAM: `qwen3-vl:8b` (точность/размер); быстрее — `qwen3-vl:4b-instruct`.

### Срез 7 — prod-раздача SPA

- FastAPI отдаёт собранный `frontend/dist` (если каталог существует): `/assets/*` — статика, остальные пути → `index.html` (SPA-fallback для клиентского роутинга).
- Маршруты `/api/*` регистрируются раньше и не затмеваются. Если `frontend/dist` нет — API работает как раньше (только `/api`).
- Один процесс для продакшена: собрать фронт (`bun run build`) и запустить `uvicorn app.api.main:app`. Проверено: `/` и `/processing` → HTML, `/api/health` → JSON, `/assets/*.js` → JS.
- Тесты: `tests/test_api_spa.py` (скипаются без сборки).

### Срез 8 — раскладка как в легаси NiceGUI

- Экран «Фото» повторяет старую NiceGUI-раскладку (§2): слева фиксированная колонка — карточка «Период» (radio «Дата загрузки» / «Дата съёмки», select «Текущий месяц / Предыдущий месяц / Все даты / Выбрать период»), ниже две прокручиваемые панели **«Адреса»** и **«Клиенты»**; справа — GRID фотографий.
- API: `GET /v1/addresses`, `GET /v1/clients` — фасеты с количеством; у `/v1/photos` добавлены `date_from`/`date_to`.
- Ограничение: дата съёмки не сохраняется (в схеме только `created_at`), поэтому радио «Дата съёмки» отключено, фильтр периода — по дате **загрузки**.
- Источники: адреса — из распознавания (HYBRID/DINO), клиенты — из QWEN. Клик по фасету фильтрует GRID; активные фильтры показаны чипами.

### Срез 9 — технический раздел

- Вкладка **«Технический»** повторяет легаси-раздел (`components/technical.py` + `technical_modules`): **Обработка, QWEN, Автоматизация, Пользователи, Данные**.
- «Обработка» — запуск/статусы DINO/HYBRID и список заданий; «QWEN» — выбор модели и выгрузка из памяти.
- «Автоматизация», «Пользователи», «Данные» — заглушки с пояснением: watcher/расписание, OIDC и экспорт/обслуживание хранилища ещё не реализованы.
- Роуты `/processing` и `/settings` редиректят на `/technical`.

### Срез 10 — подборки/закладки и выбор фото

- **Схема `009_collections.sql`**: `collections` (name, kind `Моя/Клиентская`, client, scope `addresses/clients/photos`) и `collection_members` (member_type `address/client/photo`, member_value). Идемпотентно.
- **API**: `GET /v1/collections`, `GET /v1/collections/{id}/members`; `POST /v1/collections`, `DELETE /v1/collections/{id}`, `POST /v1/collections/{id}/members`, `POST /v1/collections/{id}/members/remove` (scope `collections:write`); `/v1/photos?collection_id=` фильтрует по подборке.
- **UI**: панель «Подборки» в левой колонке (клик фильтрует, удаление), чекбоксы на карточках, «Выбрать все / Снять», счётчик выбранного, «В подборку» (существующая или новая), «Скачать выбранные» (открывает `/original`).
- Аналог легаси `collections.py` + `collections`/`collection_members`. Не перенесено: `manager_selections` (состояние чекбоксов на менеджера) — появится вместе с пользователями.

### Срез 11 — техраздел: система / слепки / последний запуск

- `GET /v1/system` — CPU/RAM/диск/uptime/load (psutil, без torch); UI-вкладка «Система» с автообновлением (2 с).
- `GET /v1/fingerprints` — инвентарь слепков из `data/fingerprints` (id, фото, размерность, версия, модель); вкладка «Слепки».
- `GET /v1/runs/last` — последний DINO batch, последний HYBRID run и счётчики очереди заданий; вкладка «Последний запуск».
- Техраздел теперь: Обработка, Последний запуск, QWEN, Автоматизация (заглушка), Система, Слепки, Пользователи, Данные (заглушка).

### Срез 12 — расширенный просмотрщик, контекстное меню, единый поиск

- **Поиск** (`q`) в `/v1/photos` теперь ищет сразу по нескольким полям: filename, client, brand, category, description, address (аналог легаси поиска по client/brand/category/description). `PhotoSummary` дополнен `brand`/`category`.
- **`GET /v1/photos/{photo_id}/details`** — фото + его QWEN-метаданные (`photo_qwen`): status, description, address, client, brand, category, tags, модель, время; `error_message` очищается от абсолютных путей (`redact_paths`).
- **Просмотрщик (rich)**: диалог с превью MIDDLE слева и панелью справа — Адрес (распознавание), Клиент, Бренд, Категория, статус/модель/время QWEN, Описание, Теги; кнопки «Оригинал»/«Сохранить».
- **Контекстное меню** на карточке (ПКМ) и в режиме списка: Открыть / Оригинал / Сохранить / В подборку.
- **Режим плитка/список** и **сортировка** (имя файла / адрес / клиент) — аналог легаси GRID.

### Срез 13 — сохранённые поиски и мультивыбор панелей

- **Схема `011_saved_searches.sql`**: `saved_searches` (name, filters JSONB, user_id, created_at), идемпотентно.
- **API**: `GET /v1/searches`; `POST /v1/searches`, `DELETE /v1/searches/{id}` (scope `searches:write` → роль «Менеджер»). `GET /v1/photos` — `address`/`client` принимают несколько значений (повторяющийся параметр, OR-семантика).
- **UI**: панели «Адреса»/«Клиенты» — чекбоксы (мультивыбор) + «Все/Снять»; чипы на выбранные значения; карточка «История поиска» (сохранить/применить/удалить); «Сохранить поиск» восстанавливает запрос, адреса, клиентов, период, подборку.

### Срез 14 — модуль «Данные» (экспорт + обслуживание хранилища)

### Срез 29 — умный поиск по фото (пункт 2, первый инкремент)

- **Поток**: кнопка-камера в строке поиска → выбор **одного** изображения (jpg/png) → имя файла появляется в строке поиска чипом «имя (фото)» → кнопка «ПОИСК» превращается в «ИИ-ПОИСК» → на время работы она становится «СТОП» (реальная отмена задания). Выбранный файл живёт в памяти браузера до нажатия кнопки, поэтому отмена до запуска не оставляет мусора на сервере.
- **Бэкенд**: `POST /v1/search/media` (multipart, одно изображение, scope `searches:write`) — файл сохраняется в `data/media_search` под уникальным именем (mkstemp, 0600), проверяется декодером, затем ставится задание `MEDIA_SEARCH` (`schema/020`); `GET /v1/jobs/media-search/{id}` (scope `read`) и `POST /v1/jobs/{id}/cancel` (scope `jobs:write`). Тяжёлая работа — только в воркере.
- **Поиск по описанию**: Qwen описывает загруженное фото (`description`, `brand`, `category`, `client`, `tags`), из этих полей строятся фильтры и выполняется поиск по сохранённым Qwen-метаданным базы. Второго вызова модели нет — описание картинки сразу становится запросом.
- **Временное хранение**: файл запроса удаляется воркером в `finally` (и при ошибке); дополнительно `prune_stale()` подчищает файлы старше 24 ч, оставшиеся после падения воркера. Ничего не пишется в таблицы фото — результат живёт только в строке задания.
- **Отмена**: `PENDING` → `CANCELLED` сразу (воркер не возьмёт задание), при этом эндпоинт сам удаляет загруженный файл — воркер, который удалил бы его в `finally`, для отменённого задания не запускается; удаляется только файл внутри `data/media_search` (проверка вложенности), чтобы подделанный payload не превратил отмену в «удали любой файл». `RUNNING` нельзя прервать внутри шага, но статус меняется, поэтому `mark_done`/`mark_failed` отказываются публиковать результат — воркер его отбрасывает и пишет в лог «cancelled». Неизвестное задание → 404, завершённое → 409. `schema/021` расширяет `job_queue.status` значением `CANCELLED`.
- **Ограничения**: пока только фото (видео — отдельный этап с выбором кадра), проценты Qwen на кнопке не показываются — модель обрабатывает один файл без промежуточных шагов, поэтому UI показывает стадию (в очереди → QWEN → поиск). Ручной режим с модалкой, правкой тегов и видео — следующий инкремент.
- **Качество выдачи**: длинное описание редко совпадает подстрокой, поэтому результат часто определяют более узкие поля (`client`, `category`) — на реальном прогоне запрос «Городская улица с пробкой, рекламный щит с изображением врача…» дал 106 фото в основном по категории. Ранжирование по числу совпавших терминов — следующий шаг.
- **Хрупкость QWEN**: некоторые модели игнорируют `think: false`, и рассуждения съедают бюджет токенов (`done_reason: length`, `content` пуст) — тогда JSON не приходит вовсе. Для запросного изображения бюджет поднят до 1024 токенов (`SCENE_SEARCH_MAX_TOKENS`), а `parse_result` кидает `QwenParseError` с сырым текстом: если структуры нет, поиск использует сам текст как фразу (`fallback: true`), а не падает.

### Срез 30 — справочник адресов (пункт 3, первый шаг)

- **Таблицы** (`schema/022`): `address_directory` (юридическое + упрощённое название, `active`, `sort_order`) и `address_fingerprints` (`fingerprint_id` PK → адрес). Подробности и откат — в `database_schema.md` §4.21.
- **API**: `GET /v1/addresses/directory`, `GET /v1/addresses/unassigned` (идентификаторы из `data/fingerprints/` без адреса), `POST/PUT/DELETE /v1/addresses/directory[/{id}]`, `PUT /v1/addresses/directory/{id}/fingerprints`. Запись — новый scope `addresses:write` (выдан Администратору через `*` и Менеджеру: курирование адресов — рабочая задача, не администрирование). Валидация: хотя бы одно название, уникальное юридическое название, идентификатор по маске `^[A-Za-z0-9._-]{1,64}$`.
- **Выдача фото**: распознанный идентификатор разрешается в имена во внешнем слое запроса (`LEFT JOIN`), поэтому карточка фото (п.8) показывает юридический адрес и alias, как только сопоставление заведено; без сопоставления — «—», как раньше.
- **Почему это первым шагом**: окно слепков (переименование/архивация/версии) и скачивание файлов по alias/юридическому имени (п.11б) опираются на этот справочник, а не наоборот.
- **Решение по размеру подборки (2026-10-14):** 20–30 фото на слепок, см. `docs/fingerprint_size_experiment.md`. Окно слепков (п.3) должно предлагать этот размер по умолчанию.

### Срез 31 — вкладка «Адреса» и имена файлов при скачивании

- **Вкладка «Адреса»** в техническом разделе (`components/AddressDirectory.vue`): список адресов с идентификаторами, создание (хотя бы одно название), правка названий, переключатель «активен», удаление, и диалог сопоставления — отмеченные идентификаторы переносятся на этот адрес с прежнего. Свободные идентификаторы берутся из `GET /v1/addresses/unassigned` (то, что лежит в `data/fingerprints/` и ещё не названо).
- **Имена файлов при скачивании** (п.11б): настройка `downloadNameMode` в `stores/display.js` (localStorage) — «Имя файла» (по умолчанию, как раньше), «Адрес (упрощённый / alias)», «Адрес (юридический)». Итоговое имя — `<адрес>__<исходное_имя>`, небезопасные для файловой системы символы заменяются на `_`, пробелы схлопываются; у фото без сопоставленного адреса имя остаётся исходным (fallback — распознанный id). Настройка живёт в том же компоненте `DisplaySettings.vue`, то есть доступна и из шестерёнки над гридом, и во вкладке «Отображение».
- Выбор режима применяется и к пакетному скачиванию (`Скачать выбранные`), и к одиночному (`Сохранить` в контекстном меню и в просмотрщике).

### Срез 33 — окно управления слепками (пункт 3, вторая часть)

- **Реестр** (`schema/023`): `fingerprints` (имя, описание, версия алгоритма, модель, размерность, число фото, папка-источник, активность) и `fingerprint_versions` (журнал пересборок: сколько фото и какие именно). Источник истины — `data/fingerprints/<id>/metadata.json`; кнопка «Синхронизировать с диском» переносит его в базу и добавляет версию только при изменении набора фото.
- **API**: `GET /v1/fingerprints/registry[/{id}][/versions]` (scope `read`), `POST /v1/fingerprints/sync`, `PUT /v1/fingerprints/registry/{id}` (scope `jobs:write`).
- **UI** (вкладка «Слепки» в техразделе): таблица с адресом и текущей версией, отметка «векторы на диске», переключатель «активен» (архивация без удаления векторов), диалог «Имя / описание / папка-источник», диалог версий с числом фото, датой и списком имён файлов. Кнопки обслуживания видит только Администратор.
- **Размер подборки**: 20–30 фото по умолчанию (решение владельца, см. `docs/fingerprint_size_experiment.md`) — это подсказано прямо в диалоге редактирования.

### Срез 34 — сборка слепка из окна (выбор папки, имена и даты фото)

- **Задание `FINGERPRINT_BUILD`** (`schema/024`): сборку выполняет тот же PostgreSQL-воркер, что и INGEST_DIR, — читать папку и гонять DINOv2 в обработчике запроса нельзя. Одно активное задание на слепок (дедуп по `fingerprint_id` в payload).
- **API**: `POST /v1/fingerprints/build` `{fingerprint_id, folder, max_photos?, replace?}` (scope `jobs:write`) — папка проверяется теми же правилами, что и рабочая папка INGEST (существование + `SCENE_SOURCE_ROOTS`), пустая папка → 400; `GET /v1/fingerprints/browse[?path=]` — список подпапок на сервере с числом фото (браузер не может передать путь серверу, поэтому навигация серверная); `POST /v1/fingerprints/pick-folder` — **системный диалог на машине сервера** (zenity), включается `SCENE_NATIVE_PICKER=1`, по умолчанию 501.
- **Папки по умолчанию нет**: в окне сборки путь пустой, файлы берутся только из выбранной папки. Ничего не копируется — строитель читает источники там, где они лежат.
- **Подвыборка без копирования**: `FingerprintManager.create(..., max_photos=N)` берёт N фото шагом по списку (не «первые N»), по умолчанию в окне предложено 30 (норма 20–30 из замера). `replace=True` пересобирает слепок: старые векторы уносятся в сторону и удаляются только после успешной публикации новых, поэтому неудачная пересборка не ломает рабочий слепок.
- **Оригиналы дальше не нужны**: строитель записывает в `metadata.json` `source_folder` и `image_meta` — имя **и дату съёмки** каждого использованного фото; реестр переносит их в `fingerprint_versions.images_meta`. Проверено сквозным прогоном: 20 фото из `data/input/80` → слепок собран, в базе 20 имён и 20 дат.
- **Бэкфилл существующих слепков**: `scripts/backfill_fingerprint_meta.py` сопоставил имена из `metadata.json` с файлами `data/input/<адрес>/`, прочитал EXIF и дописал `image_meta` + `source_folder` во все 18 слепков (100 % имён найдено; у двух фото EXIF-даты нет). Файлы перезаписаны атомарно, векторы не тронуты.

### Срез 36 — адрес из справочника в настройках слепка, импорт адресов из XLSX

- **Юридический адрес выбирается списком** в диалоге слепка (вкладка «Слепки»): `q-select` наполняется из `GET /v1/addresses/directory` («Адреса» в техразделе), вручную ничего не вводится — слепок может ссылаться только на существующий адрес. Сохранение идёт через `PUT /v1/fingerprints/registry/{id}/address` `{address_id}` (scope `addresses:write`); очистка поля снимает привязку. Один идентификатор принадлежит одному адресу, поэтому выбор другого переносит привязку.
- **Импорт адресов из XLSX/CSV**: кнопка «Импорт из XLSX / CSV» во вкладке «Адреса» → `POST /v1/addresses/import` (multipart, ≤10 МБ). Заголовки распознаются по смыслу («Юридический адрес»/«Упрощённый адрес», `legal_address`/`simple_address`, порядок колонок любой); без заголовков первая колонка — юридический адрес, вторая — упрощённый. Сопоставление существующих адресов идёт по юридическому названию (регистр и пробелы не важны), **id адреса сохраняется** — привязки фото и слепков не рвутся, обновляется только изменённое упрощённое имя. Отчёт: сколько строк, добавлено/обновлено/без изменений/ошибок.
- **Зависимость**: чтение XLSX добавлено `openpyxl>=3.1,<4` в `pyproject.toml`; CSV/TSV читаются стандартной библиотекой.
- Проверки: 14 тестов (разбор XLSX с русскими и английскими заголовками, таблица без заголовков, CSV с пустыми строками, отказ на PDF/битом XLSX, идемпотентный импорт, регистр/пробелы, эндпоинт импорта, привязка и снятие адреса, неизвестный адрес → 400, неизвестный слепок → 404).

### Срез 37 — тянущиеся границы панелей, «Авто» для плиток

- **Границы панелей тянутся**: `components/ResizeHandle.vue` (pointer events + клавиатура стрелками) сообщает смещение курсора, а размеры держит `stores/display.js` — `leftPanelWidth` (240–620 px), `rightPanelWidth` (те же пределы; тянется «от края», поэтому отрицательное смещение увеличивает ширину), `sideListHeight` (140–640 px) — высота списка адресов/клиентов, ниже которой идут «Подборки». Всё в localStorage, есть сброс.

Поэтому перетаскивание границы сразу перекладывает плитки. Фиксированные 2–6 остались как были.

### Срез 38 — прогресс сборки, пауза/отмена, батч по воркерам

- **Прогресс**: строитель вызывает `progress(done, total, stage)` между батчами (эмбеддинги — по батчам модели, дескрипторы — по фото), воркер пишет `{done, total, stage, percent}` в `job_queue.progress` (не чаще раза в секунду). В окне сборки — линейный прогресс-бар, стадия и проценты; в батче — один агрегированный бар (проценты взвешены по фото, завершённые задания считаются целиком).
- **Пауза/продолжить/отмена**: `POST /v1/jobs/{id}/pause|resume|cancel`. `PAUSED` — новое состояние: задание из очереди не берётся вовсе, а уже работающее замечает паузу между батчами и ждёт. Ожидание **ограничено** (`SCENE_PAUSE_MAX_SECONDS`, по умолчанию 300 с) — иначе одна пауза заблокировала бы очередь, ведь основной воркер однопоточный. Отмена видна между батчами и не публикует результат.
- **Батч-сборка**: `POST /v1/fingerprints/build-batch` создаёт по заданию на каждый пункт, все с общим `batch_id`; `GET /v1/fingerprints/batch/{id}` отдаёт статусы и агрегат. В окне — диалог «Батч-сборка»: выбрать папку с подпапками адресов, отметить нужные, размер подборки (по умолчанию 30) и запустить; видно, сколько готово, ошибки и «на паузе», есть «Отменить все».
- **Распределение по воркерам**: воркер умеет `--only TYPES` и `--parallel N` — N процессов в одном юните, каждый берёт своё задание (`claim_next` атомарный, с фильтром по типам). Для этого добавлен юнит **`scene-builder.service`** (`--only FINGERPRINT_BUILD --parallel 3`), он включён на этой машине. Проверено: батч из трёх слепков шёл **тремя сборками одновременно**, все завершились, агрегат 100 %.
- Проверки: 12 бэкенд-тестов (прогресс и троттлинг, отмена из состояния, ожидание и таймаут паузы, батч-эндпоинты, пауза/возобновление, фильтр claim по типам) и 3 фронтенд-теста клиента.

### Срез 39 — грид показывает все фото, подгружая их по прокрутке

- **По умолчанию без фильтра по дате**: период выставлен в «Все даты» (список периодов переупорядочен, «Все даты» первым) — грид показывает весь корпус, а не текущий месяц.
- **Страницы по 100** (`PAGE_SIZE` в `stores/photos.js`, это максимум, который принимает `GET /v1/photos`) — при 256 фото это 3 запроса вместо 6; `q-infinite-scroll` с предзагрузкой за 600 px подтягивает следующую страницу до того, как пользователь дойдёт до низа, поэтому прокрутка не спотыкается.
- Курсорная пагинация не менялась: страницы копятся в `items`, `hasMore` держится на `next_cursor`. Проверено на корпусе: 100 + 100 + 56 = 256 фото, после третьей страницы `next_cursor` пуст.
- «Выбрать» по-прежнему выбирает **загруженные** фото (подсказка об этом есть у кнопки) — выбор хранится по `photo_id`, поэтому не сбрасывается при подгрузке новых страниц.

### Срез 40 — имя слепка = алиас его адреса

- **Слепок называется по алиасу своего адреса.** При выборе юридического адреса в диалоге слепка (`set_address`) алиас из справочника (`simple_address`, иначе `legal_address`) **сразу записывается в `display_name`** — имя хранится, а не только вычисляется при чтении. Имя, набранное руками, не перетирается: привязка перезаписывает только то имя, которое записала сама, или пустое; снятие адреса убирает ровно это имя, и слепок снова называется по id.
- **Переименование алиаса тянет за собой слепки**: `update_address` при смене алиаса или юридического имени обновляет `display_name` у привязанных к этому адресу слепков, которые всё ещё носят прежнее имя (`''` или прежняя подпись адреса). Имя, набранное руками, не трогается. Так справочник остаётся единственным местом, где переименовывают адреса.
- **Запасной расчёт при чтении** (`resolve_name`): `display_name` → алиас → юридический адрес → технический id. Он нужен для слепков, привязанных до появления автозаполнения, и когда поле имени очистили вручную.
- **Список «Адреса» строится из слепков, а не из фото**: панель — это список слепков (слепок = адрес/щит), названный по имени слепка. Берутся активные слепки из реестра, поэтому слепок остаётся в списке, даже если ни одно фото ещё не распознано как он (счётчик покажет 0). Распознанный id, которого нет среди активных слепков (например, архивный), добавляется отдельной строкой — чтобы фото нельзя было потерять из фильтра. Сортировка — по показываемому имени, а не по техническому id.
- **Ответ `GET /v1/addresses`**: `{address, name, count}`. `address` — распознанный id, его и отправляет фильтр (`?address=78_v33`); `name` — имя слепка для показа. Раньше список строился по фото (`DISTINCT address`) и отдавал `simple_address`/`legal_address`.
- **Технический id виден в подсказке**: в гриде карточка фото, панель «Адреса» и просмотрщик показывают имя (алиас), а исходный `78_v33` — во всплывающей подсказке. В окне «Слепки» колонка «ID» не менялась. Фильтрация, счётчики и выбор «Все» работают по-прежнему по техническому id, поэтому ничего не сломалось для фото без привязки: там показывается id, как раньше.
- **Порядок действий**: имена появятся после привязки слепков к адресам — окно «Слепки» → карандаш → «Юридический адрес (из справочника)». До привязки всё выглядит как раньше (технические id), но список уже строится из реестра слепков.
- Проверки: pytest — порядок разрешения имени (ручное → алиас → юридический → id), форма ответа `/v1/addresses`, состав панели (все активные слепки на месте, порядок по имени); vitest — колонка «Имя» берёт `name`, а не `display_name`.

### Срез 41 — превью слепка и юридический адрес в окне «Слепки»

- **Колонка «Адрес»** в окне «Слепки» показывает **юридический адрес**; алиас теперь стоит рядом, в колонке «Имя» (имя слепка), поэтому дублировать его незачем.
- **Превью сохраняется вместе со слепком.** Сборщик (`app/core/fingerprint.py:build_preview`) делает полоску **из 4 фото в один ряд** (640×120, JPEG, ~15 КБ) тем же шагом, что и сам слепок, и кладёт `preview.jpg` в каталог слепка — то есть публикует атомарно вместе с векторами, как и остальные артефакты. Зачем: исходники не хранятся, папка-источник может быть удалена, а превью переживает её. В `metadata.json` добавлен ключ `preview` (`"preview.jpg"` либо `null`, если ни одно фото не удалось прочитать — битый исходник сборку не роняет). Формат слепка не менялся: `load()` требует прежний список файлов, `preview.jpg` — дополнение. Размер и раскладка задаются константами `PREVIEW_COLUMNS/PREVIEW_ROWS/PREVIEW_CELL/PREVIEW_QUALITY`; при их изменении надо поправить и соотношение в окне «Слепки» (`:ratio` в `FingerprintsList.vue`) и перегенерировать старые превью: `scripts/backfill_fingerprint_previews.py --force`.
- **API**: `GET /v1/fingerprints/registry/{id}/preview` (scope `read`) отдаёт картинку; путь строится из проверенного id внутри корня слепков, `Cache-Control: no-cache` — пересборка сохраняет id, поэтому кэшировать нельзя. 404, если превью нет.
- **Старые слепки**: `scripts/backfill_fingerprint_previews.py` собирает превью из папки-источника по `image_meta` (именно те файлы, что использовались). Прогнан на 18 слепках — превью есть у всех. Если исходники уже удалены, скрипт сообщает, что нужна пересборка.
- **UI**: колонка «Превью» со значком `photo_library` — при наведении всплывает окно с картинкой; если превью нет, окно говорит об этом. В диалоге редактирования слепка тот же монтаж показан блоком «Фото, из которых собран слепок». Оба места обрабатывают 404 (слепок собран до появления превью).
- Проверки: pytest — монтаж создаётся при сборке, битый источник не мешает сборке, `preview_path` строится только из валидного id, эндпоинт отдаёт `image/jpeg` с `no-cache` и 404 без превью; vitest — юридический адрес в колонке, значок превью и картинка в диалоге.

### Срез 42 — настройки пользователя на сервере, шапка, защита учётных записей

- **Настройки отображения хранятся у пользователя на сервере.** Блоб `manager_selections.state` (schema/015) получил ключ `display`: при входе `App.vue` (после `afterAuth`) вызывает `display.loadFromServer()`, а каждое изменение настроек уходит на сервер (debounce 800 мс, `PUT /v1/selection`). localStorage остаётся офлайн-копией. `PUT /v1/selection` теперь **сливает** верхнеуровневые ключи, а не заменяет блоб: выбор фото в гриде и настройки отображения пишутся разными частями интерфейса и не должны затирать друг друга. Подборки и раньше были серверными (schema/009); отдельного «Избранного» в проекте нет — его роль играют подборки.
- **Шапка**: вкладка «Технический» заменена шестерёнкой (`to="/technical"`, подсказка), а пользователь и выход уехали правее неё и выделены плашкой (`.header-user` — полупрозрачная подложка с рамкой). Тёмная тема осталась отдельной кнопкой слева от вкладок.
- **Пользователи**: кнопка-карандаш открывает диалог, где меняются имя, роль и **цвет** (раньше цвет задавался только при создании). Если администратор меняет цвет себе — тема приложения перекрашивается сразу. Цвет можно очистить (пустое значение → основной синий).
- **Администратора и Гостя нельзя архивировать**: API отвечает 400 («Администратора и Гостя нельзя архивировать»), кнопка архивации в таблице для них отключена с подсказкой. Правило по именам учётных записей (`is_builtin_user` в `app/users/database.py`), а не по роли: роль можно сменить, но эти две записи должны оставаться рабочими.
- **Восстановление доступа**: `scripts/reset_users.py --password <пароль>` — приводит «Администратора» и «Гостя» в рабочее состояние (создаёт при отсутствии, активирует, задаёт пароль, сбрасывает их сессии) и показывает остальных пользователей, не трогая их; `--archive-others` отправляет активных в архив. Пароли в репозиторий не попадают.
- Проверки: pytest — слияние частичных сохранений состояния, запрет архивации встроенных учётных записей; vitest — восстановление настроек с сервера, отправка изменений, правка цвета пользователя, отключённая кнопка архива.

### Срез 43 — «Фотогалерея», роль в админке, подвал и руководство

- **Шапка**: главный экран называется «Фотогалерея» (иконка + плашка, как у блока пользователя), технический раздел открывается шестерёнкой справа от неё, пользователь и выход — ещё правее, в своей плашке.
- **Технический раздел — только для Администратора и Менеджера.** У Гостя шестерёнки нет, и маршрут `/technical` закрыт сторожем (`router.beforeEach`): набрав адрес вручную, Гость попадёт на галерею. Справка `/help` доступна всем.
- **Вход сразу открывает галерею с восстановленными настройками**: `doLogin` дожидается `afterAuth()` (выбор фото, настройки с сервера, сводка) и делает `router.push('/')`. Пока настройки не загружены, вместо страницы показывается спиннер — иначе грид мелькал бы раскладкой по умолчанию.
- **Порядок вкладок технического раздела** задан владельцем и разделён на группы (разделители `<span class="tab-sep">`): `Загрузка · Обработка · Распознавание` | `Автоматизация · Последний запуск · Система · Настройки · Данные` | `Слепки · Адреса` | `Пользователи · Отображение`. Ingest переименован в «Загрузка», QWEN — в «Распознавание».
- **Новая вкладка «Настройки»** (`components/BaseSettings.vue`): показывает текущие параметры отображения, умеет «Запомнить текущие как базовые» и «Вернуть базовые» (базовое = заведомо рабочее стартовое состояние), а также скачать настройки файлом и загрузить из файла (файл становится новым базовым). База хранится за пользователем на сервере в том же блобе (`display_base`), локально — в `localStorage` как запасная копия.
- **Подвал-статусбар** на всю ширину (`q-footer`): слева ссылка на руководство, справа сводка — фото, адреса, клиенты и **дата последнего добавления фото** (выделена), подсказка с точным временем. Данные берутся из нового `GET /v1/stats` (`repository.stats()`: count фото, count активных адресов справочника, count различных клиентов QWEN, max(created_at)). Сводка не критична для работы: если запрос не удался, окно просто покажет прочерки.
- **Руководство пользователя** — страница `/help` (`pages/Help.vue`), открывается из подвала: вход, галерея и фильтры, выбор и действия, подборки, поиск по фото, настройки вида и базовое состояние, подвал, роли, частые вопросы. Страница занимает всю ширину (карточки в две колонки, чтобы строки не растягивались), а в конце — раздел «Стек технологий»: путь фотографии от загрузки до поиска (проверка файла и SHA-256 → уменьшенные копии → DINOv2 → сверка со слепками HYBRID → чтение данных моделью QWEN → поиск) и таблица технологий «простыми словами».
- Проверки: pytest — форма `/v1/stats`; vitest — базовое состояние (запомнить/вернуть, загрузка из файла).

### Срез 44 — скачивание выбранного одним архивом

- **«Портфель» убран из тулбара.** Подборки по-прежнему создаются плюсом в панели «Подборки» и кнопкой «Портфель» в панели (там же, где список).
- **«Скачать»** активна только когда есть выбранные фото (раньше нажатие без выбора давало всплывающее предупреждение).
- **Кнопка «ZIP»** рядом скачивает выбор одним архивом: `POST /v1/photos/archive` (scope `originals`), тело — `{items: [{photo_id, name}]}`. Имена присылает окно (те же, что при скачивании по одному: исходное или `<адрес>__<имя>`), сервер их санирует (`app/api/archive.py:safe_archive_name` — только базовое имя, без путей и `..`, ограничение длины, разведение совпадений « (2)»). Файлы берутся из зарегистрированных путей внутри `SCENE_ORIGINALS_ROOTS` — общая проверка `_allowed_original_path`, та же, что у одиночного скачивания.
- **Архив собирается на сервере** в spooled-файле (до 64 МБ в памяти, дальше на диск) и отдаётся потоком; файлы кладутся **без пережатия** (фото уже сжаты, deflate только жёг бы CPU). Ограничения: ≤ 500 файлов и ≤ 2,5 ГБ на архив (иначе 413), пустой выбор — 400, нет настроенных корней — 503. `Cache-Control: no-store`.
- Проверки: pytest — имена (обрезка путей, длина, разведение совпадений), сборка архива настоящими файлами, отказы на пустой выбор/перебор/недоступный файл/отсутствие корней. Живая проверка: три фото → `200 application/zip`, 12 МБ, внутри файлы с заданными именами.

### Срез 45 — подборки = сохранённый выбор адресов или клиентов

- **Смысл подборки изменился.** Раньше подборка была набором `photo_id` и подмешивалась в фильтр фото. Теперь подборка хранит **выбор адресов или клиентов**: адресные живут в левой панели, клиентские — в правой. Клик по подборке отмечает её адреса (или клиентов) в списке и применяет фильтр; фотографии в гриде показываются по этому выбору. На сами фото подборка не влияет и в `/v1/photos` не передаётся.
- **Хранилище не менялось**: те же `collections` (scope `addresses|clients`) и `collection_members` (member_type `address|client`), тот же API. Подборки, созданные ранее, остаются читаемыми; фильтр `collection_id` в `/v1/photos` сохранён в API, но UI его больше не передаёт.
- **`components/CollectionsPanel.vue`** принимает prop `scope` и показывает подборки своего вида (геттер `collectionsFor(scope)`), заголовок «Подборки адресов» / «Подборки клиентов», плюс сохраняет текущий выбор, корзина удаляет подборку.
- **`stores/photos.js`**: `applyCollection()` (повторный клик по активной подборке снимает выбор), `saveSelectionAsCollection({name, scope, collectionId})` (создаёт подборку или заменяет состав существующей: сперва удаляет старые элементы, затем добавляет текущий выбор), `collectionsFor`. Удалены `selectCollection` и `addSelectedToCollection` — подборка больше не собирается из фото.
- **Диалог «В подборку»** (`PhotosGrid.vue`) выбирает вид по области, показывает имена отмеченных адресов (в выборе лежит технический id вида `79_v33`, рядом выводится читаемое имя), даёт выбрать существующую подборку того же вида или ввести название новой. Меню снимка предлагает сохранить его адрес в подборку адресов.
- Проверки: vitest — область подборок, восстановление выбора адресов и клиентов, снятие по повторному клику, отсутствие `collection_id` в запросе фото, создание и замена состава (88 тестов, 9 файлов).
