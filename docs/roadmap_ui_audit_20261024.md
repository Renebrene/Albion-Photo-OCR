# Аудит UI и план исправлений (2026-10-24)

## Как проводился

Три независимых прохода по разным слоям (грид; сторы и API-клиент; компоненты и
рендер) плюс проверка каждой находки по коду: смотрели, нет ли рядом
компенсации, из-за которой поведение на самом деле корректное. Находки, где
компенсация есть, в список не попали (см. «Что проверено и не подтвердилось»).

Найдено 36 пунктов: 2 — P1, 24 — P2, 10 — P3. Второй, независимый проход
(раздел «Дополнение») добавил ещё 14 пунктов P2 и 22 — P3 и подтвердил
основные находки первого. Три из них — регрессии наших
недавних правок (помечены «наша правка»), они идут в работу первыми.

Область: `frontend/src` (страницы, компоненты, сторы, api-клиент). Бэкенд
затрагивается только там, где нужен новый контракт (сортировка выдачи).

Ответы сверены до последнего счётчика: восемь случаев выборки (грид с

Правка — без миграции: адресный слепок, сходство и отрыв берутся одним

«последний вердикт HYBRID» — сходство (join к `dino_candidates` rank=1),
отрыв и адрес. Это три прохода по 56 870 строк; в одном проходе
985 239 буферов (~7.5 ГБ касаний). Индексы на месте
(`idx_hybrid_results_photo_latest`, `dino_candidates_pkey`,
`photo_address_overrides_pkey`), дело в числе обращений, а не в их виде.

адрес» — не чистая функция вердикта. Материализованное значение придётся
сбрасывать при смене порогов, иначе счётчики панели разойдутся с гридом.

### Индексы под сортировки грида (2026-10-24, вечер)

Второй аудит нашёл P1: с включённым фильтром «распознанные» сортировки по имени
файла и по дате отвечали 2.7 с. Причина — порядок задавала производная таблица
(`_PHOTO_DERIVED` поверх `_PHOTO_BASE` с шестью коррелированными подзапросами на
строку), поэтому до `LIMIT 101` материализовались все 56 870 строк: 1 930 548
обращений к буферам в плане. Сортировка по `photo_id` всегда была быстрой —
порядок давал первичный ключ, и планировщик останавливался на сотой
распознанной строке.

Проверял экспериментом **без следов в базе**: `CREATE INDEX` внутри транзакции,
замер на том же SQL, который выполняет грид, затем `ROLLBACK` (индексов после
себя не оставил — проверено). Отсюда миграция
`schema/052_grid_sort_indexes.sql`: два btree, `(filename, photo_id)` и
`(COALESCE(taken_at, created_at), photo_id)`; построение заняло 35 мс.

| Сортировка | Было | Стало |
| --- | --- | --- |
| по имени файла | 2 730 мс | **32 мс** |
| по дате | 2 696 мс | **37 мс** |
| по адресу | 2 992 мс | 2 882 мс |
| по клиенту | 2 730 мс | 2 606 мс |
| по `photo_id` | 18 мс | 33 мс |
| `count_photos` под фильтром | 1 514 мс | 1 556 мс |

Выдача сверена побайтово: пять сортировок по 100 строк — идентификаторы, имена и
курсоры совпали с состоянием до индексов.

**Что индексы не лечат.** Сортировки по адресу и по клиенту и счётчик упираются
не в порядок, а в материализацию: признак «распознано» читается из производной
таблицы, поэтому условие нельзя применить до дорогих подзапросов. Кандидат
`photo_qwen (client, photo_id)` проверен тем же экспериментом — 1,0×, не
помогает. Здесь нужен вариант B: сначала лёгкая выборка `photo_id` с `LIMIT`,
потом дорогая проекция только для отобранных строк, с побайтовой сверкой JSON.

## Процесс

Каждый пункт обсуждаем перед реализацией: что меняем, какие есть варианты,
