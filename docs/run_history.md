# История запусков и логи (schema/037)

**Статус:** миграции `037_run_history` и `038_run_history_keep_jobs` применены
к рабочей БД 2026-10-17 после проверенных backup; `scene-api` и `scene-worker`
перезапущены. API health и чтение списка истории проверены. Исторический
табличный лог содержит 11 записей на момент rollout.

## Назначение

`run_history` — пользовательский индекс истории запусков (pipeline, ingest, sort,
qwen, scheduler), а не новая очередь и не источник истины исполнения. Задачи
по-прежнему исполняет `public.job_queue`, а stages — `pipeline_runs` и
`pipeline_run_stages`. `run_history_jobs` связывает одну запись запуска с одной
или несколькими задачами очереди. Подключены ручной INGEST/QWEN, ручные DINO и
HYBRID (kind `sort`), фактические scheduler ticks и supervisor pipeline; UI
списка и логов доступен на вкладке «Последний запуск».

Каждая строка содержит режим (`manual`, `schedule`, `outofqueue`), статус,
счётчики JSONB, стадии и длительности, число ошибок, сообщение, автора и время.
Персональные пути и payload провайдера не хранятся в истории.

## Логи

Логи записываются в закрытый каталог `data/logs` (можно переопределить
`SCENE_RUN_LOG_ROOT`), с правами каталога `0700` и файлов `0600`. Имя строится
из ID запуска и типа; API не принимает путь от клиента и не раскрывает его.
Записи ограничены 2 MiB на запуск (`SCENE_RUN_LOG_MAX_BYTES`, байты),
редактируют абсолютные пути и типовые bearer/API-key поля; хранение — 30 дней.
`prune_stale()` удаляет только старые обычные `.log` файлы, не symlink.

Лог формируется из структурированных событий стадий/задач и ошибок отдельных
файлов, а не из общего stdout параллельных процессов (который нельзя безопасно
разделить по запуску). Ошибки файлов ограничиваются первыми 200 событиями на
задачу. Сырые запросы, ответы и ключи провайдера в лог не копируются.

## API

- `GET /api/v1/runs/history?kind=&limit=` — список последних запусков; обычный
  `read` scope.
- `GET /api/v1/runs/history/{run_id}/log` — текст лога по внутреннему ID;
  требует `jobs:read`, отдаёт `Cache-Control: no-store`; путь файла наружу не
  передаётся.

History/statuses синхронизируются при запуске и завершении job/обновлении pipeline,
но unified list — snapshot-on-request, без периодического polling компонента.
Фактическая «в реальном времени» частота зависит от job worker events; per-kind
последние ручные/scheduled/out-of-queue даты требуют отдельной агрегирующей
сводки, текущий UI её не вычисляет.

Список и лог доступны после применения схемы; API smoke на рабочем экземпляре
вернул 200 и 11 записей. Тесты проверяют scope и отсутствие принятия клиентского
пути. UI на вкладке «Последний запуск» отображает историю с типом, режимом,
статусом, счётчиками и стадиями. Лог открывается отдельным plain-text диалогом;
404 и 403 показываются как понятные состояния. Текущая роль Гость не видит
технический раздел; для иных ролей просмотр логов ограничен `jobs:read`.

Ручные DINO batches и HYBRID runs записываются под общим kind `sort` с
различимыми заголовками `DINO batch #…` / `HYBRID run #…`; это сохраняет CHECK
constraint 037 без новой миграции. Фактический тик планировщика (прошёл due и
advisory-lock gates) имеет один `scheduler` run; созданные им DINO/QWEN jobs
ссылаются на этот run и завершают его через worker. `disabled`, `not_due`,
`locked` остаются только skip-ответами API/worker и в истории не появляются.
Ошибки частичной постановки логируются как `PARTIAL`/`FAILED` при сохранении
уже созданных jobs.

## Проверка и выкладка

Миграции аддитивны и backfill не требуется. `037` проверена в отдельной схеме
на создание/повтор/откат; перед применением создан и проверен backup
`photobase_before_037_20261017_013459.dump`. После rollout выявили, что FK на
`job_queue(id)` удалял бы ссылки истории при очистке старых заданий; создан
и применён forward-fix `038_run_history_keep_jobs` после backup
`photobase_before_038_20261017_013719.dump`. Теперь `run_id` остаётся FK к
истории с `ON DELETE CASCADE`, а `job_id` намеренно не FK: старые id могут
сохраняться как архивные ссылки.

Проверено на rollout 2026-10-17: миграции 001–038 применены; у
`run_history_jobs` остались PK и FK `run_id`, FK `job_id` отсутствует. На
последней проверке этого checkout (commit `be228d5`) backend suite — 585 passed,
4 skipped; API health — 200, `scene-api`/`scene-worker` active. Полная frontend
suite — 125 passed, production build успешен (Vite предупреждает о JS chunk >500
KB).

Для полного отката сначала остановить новые записи и откатить приложение, затем
удалять таблицы `run_history_jobs` и `run_history` только после проверки
зависимостей; файлы логов можно отдельно сохранить или удалить по решению
владельца.
